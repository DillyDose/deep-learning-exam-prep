Keras Callbacks, TensorBoard และ Hyperparameter Tuning

บทนี้คือ "เครื่องมือช่วยเทรน" — ตอนนี้คุณรู้แล้วว่า network ทำงานอย่างไร (Lesson 1–5) บทนี้สอนว่าระหว่างเทรนจะสั่งให้ Keras ทำอะไรอัตโนมัติได้บ้าง (หยุดเมื่อไม่ดีขึ้น, เซฟโมเดล, ลด learning rate, ดูกราฟ) และก่อนเทรนจะเลือกค่า hyperparameter (จำนวน layer, learning rate, dropout …) อย่างมีระบบได้อย่างไร.

ก่อนเริ่ม — 3 คำที่ต้องแยกให้ออก
  • Epoch = เทรนวนครบข้อมูลทั้งชุด 1 รอบ

1. Callback คืออะไร: "ผู้ช่วยข้างสนาม" ที่ Keras เรียกให้เอง

แนวคิด: การเทรนคือ loop ซ้อน loop — วนทุก epoch, ในแต่ละ epoch วนทุก batch. Callback คือ object ที่เราแนบให้ model.fit() แล้ว Keras จะเรียกฟังก์ชันของมันเองอัตโนมัติ ทุกครั้งที่ถึงจุดที่กำหนด (เช่น "จบ epoch แล้ว") โดยเราไม่ต้องแก้ loop ของ Keras.

ตัวอย่างในสไลด์หน้า 1: สมมติ X มี 150 ตัวอย่าง (ข้อมูลที่ใช้สอนในคาบ), batch_size=64 และเทรน 3 epoch:

คำนวณ: callback ถูกเรียกกี่ครั้ง และพิมพ์อะไร
กำหนด: \(m = 150\), \(B = 64\), epochs = 3
  1. หาจำนวน batch ต่อ epoch
    $$\text{batches} = \left\lceil \frac{150}{64} \right\rceil = \lceil 2.34 \rceil = 3$$
  2. ไล่ลำดับการเรียก

    on_train_begin ถูกเรียก 1 ครั้ง ตอนเริ่ม → พิมพ์ training start

    จากนั้นแต่ละ epoch: on_train_batch_end 3 ครั้ง (พิมพ์ End of batch:1, :2, :3) แล้ว on_epoch_end 1 ครั้ง (พิมพ์ End of epoch:1)

  3. นับรวม

    batch ทั้งหมด \(3 \times 3 = 9\) ครั้ง, epoch 3 ครั้ง, train_begin 1 ครั้ง

คำสั่งพิมพ์ทั้งหมด = \(1 + 9 + 3 = 13\) บรรทัด

ข้อมูลที่ callback ได้รับ (logs): ที่ on_train_batch_end มี loss และ accuracy ของ batch นั้น; ที่ on_epoch_end มีเพิ่ม val_loss และ val_accuracy (เพราะ validation ทำหลังจบ epoch). ที่ on_train_begin logs ว่างเปล่า.

2. EarlyStopping: หยุดเมื่อไม่ดีขึ้นตามเกณฑ์ที่กำหนด

ความหมายของ 4 พารามิเตอร์ในสไลด์:

พารามิเตอร์ค่าในสไลด์ความหมาย
monitor'val_loss'ค่าที่ใช้ตัดสินว่า "ดีขึ้นหรือไม่" (เล็กลง = ดี)
min_delta0.001ต้องดีขึ้นอย่างน้อยเท่านี้ ถึงนับว่า "ดีขึ้นจริง" (กัน noise)
patience5ยอมให้ "ไม่ดีขึ้น" ติดกันได้กี่ epoch ก่อนหยุด
restore_best_weightsTrueหยุดแล้วให้ย้อน weight กลับไปที่ epoch ที่ดีที่สุด

กติกาที่ใช้ตัดสินแต่ละ epoch:

$$\text{improvement}_t = \text{best} - \text{val\_loss}_t \;\ge\; \text{min\_delta}$$
  • ถ้าเป็นจริง → นับเป็น "ดีขึ้น": อัปเดต best และรีเซ็ตตัวนับ patience เป็น 0
  • ถ้าไม่จริง → ตัวนับ patience +1; พอตัวนับ = patience ก็หยุดเทรน
คำนวณตามตารางในสไลด์ ทีละ epoch (patience = 5, min_delta = 0.001)
เริ่มที่ epoch 28: \(\text{val\_loss} = 0.4806\) ⇒ \(\text{best} = 0.4806\), ตัวนับ = 0
  1. Epoch 29: val_loss = 0.4855
    $$\text{improvement} = 0.4806 - 0.4855 = -0.0049 < 0.001$$

    ไม่ดีขึ้น (แย่ลง) ⇒ ตัวนับ = 1

  2. Epoch 30: val_loss = 0.4763
    $$\text{improvement} = 0.4806 - 0.4763 = 0.0043 \ge 0.001$$

    ดีขึ้นจริง ⇒ best = 0.4763, ตัวนับ รีเซ็ตเป็น 0

  3. Epoch 31: val_loss = 0.4750
    $$\text{improvement} = 0.4763 - 0.4750 = 0.0013 \ge 0.001$$

    ดีขึ้นจริง (ผ่านเกณฑ์แค่นิดเดียว) ⇒ best = 0.4750, ตัวนับ = 0

  4. Epoch 32–35: val_loss = 0.4887, 0.4982, 0.4904, 0.4957

    ทุก epoch แย่กว่า best (0.4750) เช่น \(0.4750 - 0.4887 = -0.0137\) ⇒ ตัวนับเพิ่มเป็น 1, 2, 3, 4 ตามลำดับ

  5. Epoch 36: val_loss = 0.5149
    $$0.4750 - 0.5149 = -0.0399 < 0.001 \;\Rightarrow\; \text{ตัวนับ} = 5 = \text{patience}$$

    ถึงเกณฑ์ ⇒ STOP

หยุดที่ epoch 36 แต่ด้วย restore_best_weights=True ได้ weight ของ epoch 31 (val_loss 0.4750) กลับมา — epoch 32–36 (5 epoch) เทรนแล้วทิ้งไป.

เปลี่ยนค่าแล้วเกิดอะไร (ใช้ตารางเดิม): ฝึกคิดแบบข้อสอบ
  1. ลด patience เป็น 3

    epoch 29 นับ 1 → epoch 30, 31 ดีขึ้นรีเซ็ต → epoch 32, 33, 34 นับ 1, 2, 3 ⇒ หยุดที่ epoch 34 (เร็วขึ้น 2 epoch) weight ที่คืนมายังเป็น epoch 31 เหมือนเดิม

  2. เพิ่ม min_delta เป็น 0.01

    epoch 30: \(0.4806 - 0.4763 = 0.0043 < 0.01\) ไม่นับว่าดีขึ้น (ตัวนับ 2); epoch 31: \(0.4806 - 0.4750 = 0.0056 < 0.01\) ไม่นับ (ตัวนับ 3) — เพราะ best ยังค้างที่ 0.4806; epoch 32, 33 ตัวนับเป็น 4, 5 ⇒ หยุดที่ epoch 33 และคืน weight ของ epoch 28 (val_loss 0.4806 ซึ่งแย่กว่า 0.4750)

บทเรียน: min_delta ใหญ่เกินไปจะมองความก้าวหน้าเล็กๆ ที่จริงเป็นของจริงว่าเป็น noise แล้วหยุดเร็วเกินและได้โมเดลที่แย่กว่า.

กลไกที่ต้องอธิบายได้
ทำไมต้องมี
loss บนข้อมูล validation ไม่ได้ลดเรียบๆ — มันแกว่งขึ้นลงเล็กน้อยทุก epoch (ดูตาราง: 0.4855, 0.4763, 0.4750, 0.4887 …). ถ้าหยุดทันทีที่ "แย่ลง 1 ครั้ง" จะหยุดเพราะ noise; patience ให้เวลาดูแนวโน้ม, min_delta กันไม่ให้การขยับ 0.0001 นับเป็นความก้าวหน้า, และ restore_best_weights แก้ปัญหาที่ตอนหยุด weight เป็นของ epoch ที่แย่กว่าที่สุดของรอบ.
เปลี่ยนแล้วเกิดอะไร
patience เล็ก/min_delta ใหญ่ → หยุดเร็ว เสี่ยง underfit (ตัวอย่างข้างบน: หยุด epoch 33 ได้ 0.4806); patience ใหญ่ → เปลืองเวลา แต่ปลอดภัยกับ noise. ถ้าไม่ตั้ง restore_best_weights ได้ weight ของ epoch สุดท้าย (36, val_loss 0.5149 = แย่ที่สุดในตาราง).
เชื่อมกับ
เหตุผลเชิงสถิติเดียวกับ Lesson 4 §6 (early stopping = regularization ชนิดหนึ่ง: หยุดก่อนที่โมเดลจะเริ่ม overfit) และ Lesson 5 §5 ที่หา "best epoch" ด้วยมือจากกราฟ val_loss — callback นี้ทำสิ่งนั้นอัตโนมัติ.

3. บันทึกโมเดล: save, save_weights และ ModelCheckpoint

สองวิธีเซฟ ต่างกันที่ "เก็บอะไร":

save_weights('x.weights.h5')save('x.keras')
เก็บเฉพาะตัวเลข weight/biasโครงสร้าง + weight + สถานะ optimizer
ตอนโหลดต้อง build_model() ก่อน แล้ว load_weights(...)load_model('x.keras') ได้เลย

อ่านตัวเลขจาก model.summary() ในสไลด์ให้เป็น (Total 785 มาจากไหน):

คำนวณ: ทำไม Trainable = 261 และ Optimizer = 524
โมเดลในสไลด์: input 2 → Hidden1 (10) → Hidden2 (10) → Hidden3 (10) → Output (1)  |  สูตรพารามิเตอร์ของ Dense: \(n_{in} \times n_{out} + n_{out}\) (weight + bias)
  1. นับพารามิเตอร์ทีละ layer
    $$\begin{aligned} \text{Hidden1} &= 2\times10 + 10 = 30\\ \text{Hidden2} &= 10\times10 + 10 = 110\\ \text{Hidden3} &= 10\times10 + 10 = 110\\ \text{Output} &= 10\times1 + 1 = 11 \end{aligned}$$

    ตรงกับคอลัมน์ Param # ในสไลด์ (30, 110, 110, 11)

  2. รวมเป็น Trainable params
    $$30 + 110 + 110 + 11 = 261$$
  3. Optimizer params (Adam)

    Adam เก็บค่าเฉลี่ยเคลื่อนที่ 2 ชุดต่อทุกพารามิเตอร์ (ของ gradient และของ gradient² — Lesson 4 §5) = \(2 \times 261 = 522\) และเก็บตัวแปรเดี่ยวอีก 2 ตัว (ตัวนับรอบ กับ learning rate) ⇒ 524

  4. Total
    $$261 + 524 = 785$$

Total params 785 = Trainable 261 (ใช้ตอน predict) + Optimizer 524 (มีเฉพาะเมื่อเซฟด้วย .save เพื่อให้เทรนต่อได้).

ModelCheckpoint คือการเซฟอัตโนมัติ: ค่าเริ่มต้นเซฟทุกจบ epoch. ถ้าตั้งชื่อไฟล์ตายตัวเช่น 'my_model.keras' ทุก epoch เขียนทับไฟล์เดิม ดังนั้นเมื่อเทรนจบ ไฟล์คือโมเดลของepoch สุดท้าย (ไม่ใช่ epoch ที่ดีที่สุด) — ใช้ตัวเลือกในหน้าถัดไปเพื่อเปลี่ยนพฤติกรรมนี้.

ตัวอย่างในสไลด์ตั้ง monitor='val_accuracy' (ยิ่งสูงยิ่งดี) จึงต้องคู่กับ mode='max' — ทั้งสามตัวเลือกทำงานร่วมกันดังนี้:

ตัวเลือกทำอะไรตัวอย่างในสไลด์
save_best_only=Trueเซฟเฉพาะเมื่อค่า monitor ดีที่สุดเท่าที่เคยเห็นTrue
monitorค่าที่ใช้เทียบ'val_accuracy'
modeอยากให้ค่านั้น 'max' หรือ 'min' (auto = เดาจากชื่อ)'max' (accuracy ยิ่งสูงยิ่งดี)

คู่กับ EarlyStopping อย่างไร: EarlyStopping ตัดสินใจเมื่อไหร่หยุด ส่วน ModelCheckpoint(save_best_only) เก็บตัวที่ดีที่สุดไว้บนดิสก์ — ถ้าไม่ใช้ save_best_only ไฟล์จะเป็น weight ของ epoch ที่ตามหลัง best ไป patience epoch (เช่น epoch 36 แทน 31 ในตัวอย่าง §2).

คำนวณ: save_freq=6, epochs=5, batch_size=64 จะเซฟไฟล์อะไรบ้าง
กำหนด: ข้อมูล train \(m = 150\) แถว, ชื่อไฟล์ my_model.{epoch}.{batch}.weights.h5
  1. หาจำนวน batch ต่อ epoch
    $$\lceil 150/64 \rceil = 3 \text{ batch ต่อ epoch}$$
  2. นับ batch สะสมตลอดการเทรน

    5 epoch × 3 = 15 batch (นับต่อเนื่องข้าม epoch: batch ที่ 1, 2, 3 = epoch 1; ที่ 4, 5, 6 = epoch 2; …)

  3. เซฟทุกครั้งที่นับสะสมครบ 6

    ที่ batch สะสม 6 และ 12 (18 ไม่ถึงเพราะมีแค่ 15)

  4. แปลงเป็น (epoch, batch ภายใน epoch)

    batch สะสมที่ 6 = ตัวสุดท้ายของ epoch 2 ⇒ my_model.2.3.weights.h5

    batch สะสมที่ 12 = ตัวสุดท้ายของ epoch 4 ⇒ my_model.4.3.weights.h5

ได้ 2 ไฟล์: my_model.2.3.weights.h5 และ my_model.4.3.weights.h5 (ตรงกับผล ls ที่สอนในคาบ). สังเกต: การเซฟไม่ได้ตรงกับขอบ epoch เสมอไป ขึ้นกับว่า save_freq หาร 3 ลงตัวหรือไม่.

4. BackupAndRestore: เทรนต่อได้หลังถูกขัดจังหวะ

ต่างจาก ModelCheckpoint อย่างไร: ModelCheckpoint เก็บโมเดล (weight) ไว้ใช้งาน แต่ BackupAndRestore เก็บสถานะการเทรน (weight + เลข epoch ที่ทำถึง + optimizer) เพื่อให้เทรนต่อจากจุดที่ขาด และมีไฟล์ backup แค่ 1 ไฟล์ ที่ถูกเขียนทับทุกครั้ง.

คำนวณ: เทรน 10 epoch แต่ถูกขัดที่ epoch index 4 แล้วสั่ง fit ใหม่
กำหนด: epochs=10, backup ทุก epoch, ถูกขัดจังหวะ (raise error) ตอนเริ่ม epoch ที่ index = 4 (index นับจาก 0)
  1. ก่อนถูกขัด: เทรนเสร็จไปกี่ epoch

    epoch index 0, 1, 2, 3 = 4 epoch และ backup ล่าสุดบันทึกว่า "ทำถึง epoch 4"

ทำไมต้องปรับ learning rate: ช่วงแรกอยากก้าวใหญ่ (เข้าใกล้จุดต่ำสุดเร็ว) ช่วงท้ายอยากก้าวเล็ก (ไม่กระโดดข้ามจุดต่ำสุด) — Lesson 4 §5 เห็นแล้วว่า Adam/RMSProp ปรับให้ต่อพารามิเตอร์; callback นี้ปรับให้ต่อ epoch.

5.1 LearningRateScheduler: ตั้งสูตรเอง

สูตรในโค้ดของสไลด์ (เมื่อ \(\alpha\) = learning rate ปัจจุบัน, \(r\) = decay_rate, \(s\) = decay_steps, \(e\) = epoch index เริ่มที่ 0):

$$\alpha_{\text{new}} = \alpha \cdot r^{\left\lfloor \frac{1+e}{s} \right\rfloor}$$

ทุกๆ \(s\) epoch คูณ learning rate ด้วย \(r\) เพิ่มอีก 1 ชั้น (\(\lfloor\ \rfloor\) = ปัดลง)

คำนวณ: learning rate ของ 5 epoch แรก เมื่อ \(r = 0.9\), \(s = 2\), เริ่มที่ 0.03
สำคัญ: Keras ส่ง learning rate ปัจจุบัน เข้ามาเป็นอาร์กิวเมนต์ตัวที่สองของฟังก์ชัน (สไลด์: "takes epoch index and current learning rate") — ค่า lr=0.01 ที่ตั้งเป็น default จึงถูกเมินเสมอ
  1. หาเลขชี้กำลัง \(\lfloor (1+e)/2 \rfloor\) ของแต่ละ epoch
    epoch index \(e\)01234
    \(\lfloor (1+e)/2 \rfloor\)01122
  2. คูณต่อจาก learning rate ของ epoch ก่อนหน้า
    $$\begin{aligned} e=0:&\;\; 0.03 \times 0.9^{0} = 0.03\\ e=1:&\;\; 0.03 \times 0.9^{1} = 0.027\\ e=2:&\;\; 0.027 \times 0.9^{1} = 0.0243\\ e=3:&\;\; 0.0243 \times 0.9^{2} = 0.019683\\ e=4:&\;\; 0.019683 \times 0.9^{2} = 0.0159432 \end{aligned}$$
  3. เทียบกับที่ "คิดว่าจะได้" ถ้ารีเซ็ตจากค่าเริ่มต้น 0.03 ทุกครั้ง
    $$0.03,\; 0.027,\; 0.027,\; 0.0243,\; 0.0243$$

    ไม่ตรงกัน! เพราะของจริงคูณซ้อนทุก epoch

ลำดับจริงที่ Keras ให้: 0.03, 0.027, 0.0243, 0.019683, 0.0159432 (ตรงกับที่ log ในคาบพิมพ์) — และเมื่อเทรนต่อถึง epoch 50 ค่านี้เหลือประมาณ \(7.6\times10^{-31}\) จน weight ไม่ขยับอีกเลย.

กลไกที่ต้องอธิบายได้ — ทำไม lr ถึงหายวับ
ทำไมต้องมี
เพราะ scheduler ส่ง learning rate ปัจจุบัน เข้ามา สูตร alpha = lr * decay_rate**exp จึงคูณต่อจากค่าเดิมทุก epoch (compounding) ไม่ใช่คิดจากค่าตั้งต้นครั้งเดียว. ถ้าต้องการ "ลดทีละขั้นจากค่าตั้งต้น" ต้องเก็บค่าเริ่มต้นไว้นอกฟังก์ชัน หรือใช้ตัวคูณคงที่ต่อ epoch.
เปลี่ยนแล้วเกิดอะไร
ค่า default ของสไลด์ decay_steps=10000 ทำให้ \(\lfloor (1+e)/10000 \rfloor = 0\) สำหรับ epoch ที่น้อยกว่า 9,999 ⇒ \(r^0 = 1\) ⇒ learning rateไม่เปลี่ยนเลยตลอด 50 epoch. ในทางกลับกัน \(s=2\) ทำให้เลขชี้กำลังโตเรื่อยๆ (0, 1, 1, 2, 2, 3, … ถึง 25 ที่ epoch 50) แล้วคูณซ้อน ⇒ lr ดิ่งจนเทรนไม่ได้ (val_loss ค้างที่ 0.6549 ในสคริปต์คาบ).
เชื่อมกับ
learning rate \(\alpha\) ในสูตรอัปเดต \(\theta := \theta - \alpha\,\nabla J\) (Lesson 1) — \(\alpha \to 0\) เท่ากับ \(\Delta\theta \to 0\) เทรนแล้วโมเดลไม่ขยับ; ต่างจากอาการ vanishing gradient (Lesson 5) ที่ตัว gradient เล็กเอง แต่ผลที่เห็นเหมือนกัน (loss ไม่ลด).

5.2 ReduceLROnPlateau: ลดเมื่อ "ติดแหง็ก" (ไม่ต้องเขียนสูตรเอง)

กติกา: ถ้า monitor ไม่ดีขึ้น (ตามเกณฑ์ min_delta) ติดกัน patience epoch ให้ลดตามสูตร

$$\alpha_{\text{new}} = \max\!\left(\alpha \times \text{factor},\; \text{min\_lr}\right)$$
คำนวณ: factor=0.1, min_lr=0.001 เริ่มที่ 0.03 (ตามสไลด์)
  1. ติดแหง็กครั้งที่ 1
    $$\max(0.03 \times 0.1,\; 0.001) = \max(0.003,\; 0.001) = 0.003$$
  2. ติดแหง็กครั้งที่ 2
    $$\max(0.003 \times 0.1,\; 0.001) = \max(0.0003,\; 0.001) = 0.001$$

    0.0003 ต่ำกว่าพื้น ⇒ ถูก "ดันขึ้น" มาที่ 0.001

  3. ติดแหง็กครั้งที่ 3 ขึ้นไป
    $$\max(0.001 \times 0.1,\; 0.001) = 0.001$$

learning rate ไล่ 0.03 → 0.003 → 0.001 แล้วค้างที่ 0.001 ตลอดไป (ตรงกับคอลัมน์ learning_rate ตอนท้ายการเทรนในคาบ).

ข้อดีเทียบกับ 5.1: ไม่มีปัญหา "คูณซ้อนโดยไม่รู้ตัว" และไม่ต้องเดาล่วงหน้าว่าจะลดตอนไหน — มันลดตอน validation หยุดพัฒนาจริงๆ; ข้อเสียคือต้องตั้ง patience/min_delta ให้เหมาะ. CSVLogger (CSVLogger("results.csv")) แค่เขียนตัวเลข logs ของทุก epoch ลงไฟล์ csv ให้เอาไปวิเคราะห์ต่อ — ไม่มีการคำนวณ.

อ่านกราฟ loss สองแบบในสไลด์: แบบซ้าย "Model does not learn anything" — loss แกว่งอยู่ระหว่างประมาณ 10 ถึง 15 ตลอดตั้งแต่ step ที่ 400 ถึง 2,800 โดยไม่มีแนวโน้มลดลง แปลว่า weight ไม่ได้พัฒนา; แบบขวา "Model learns" — loss ตกจากเกิน 25 ลงมาราว 10 ภายใน ~1,000 step แล้วค่อยๆ แบนราบ = การเรียนรู้ปกติ. ถ้ากราฟ loss ของคุณหน้าตาแบบซ้าย ให้สงสัย learning rate, การ initialize หรือ vanishing gradient (§7) ก่อนจะไปแก้เรื่องอื่น.

อ่าน histogram ของ weight/bias: แต่ละแถบสีคือ "ช่วงเปอร์เซ็นไทล์" ของค่า weight ทั้ง layer ที่แต่ละ epoch (แกนนอน = epoch) — ขอบบนสุดคือค่าสูงสุด, ขอบล่างสุดคือค่าต่ำสุด, ตรงกลางคือ median (50%). แถบที่ "บานออก" เมื่อ epoch เพิ่มขึ้น = weight กำลังกระจายออก (เรียนรู้); แถบ "แบนคงที่" = weight ไม่ขยับ.

7. ทดลองดู Vanishing/Exploding Gradient ด้วย TensorBoard

โจทย์: ทำไมโมเดลนี้เทรนไม่ขึ้น ทั้งที่ทุกอย่างดูปกติ? ตัวการคือบรรทัด kernel_initializer=RandomUniform(0,1) — ค่า weight เริ่มต้นสุ่มจาก 0 ถึง 1 ซึ่งเป็นบวกทั้งหมด เฉลี่ย 0.5 (ต่างจาก Lesson 5 §2 ที่ต้องการ weight เฉลี่ย 0 และ variance ที่คุมไว้).

คำนวณประมาณการ: weight เป็นบวกทั้งหมด ทำให้ tanh อิ่มตัวได้อย่างไร
สมมติ (เพื่อดูกลไก): แต่ละ layer มี 5 unit, activation จาก layer ก่อนหน้าประมาณ 0.9 ทุกตัว, weight เฉลี่ย 0.5, bias 0
  1. หา z ของ unit หนึ่งตัว
    $$z \approx \sum_{j=1}^{5} \theta_j\, a_j = 5 \times (0.5 \times 0.9) = 2.25$$

    เพราะ weight เป็นบวกหมด ผลรวมจึงไม่หักล้างกัน (ต่างจาก weight ที่บวก/ลบผสม)

  2. หา activation
    $$a = \tanh(2.25) = 0.978$$

    ใกล้ขอบ 1 แล้ว (และ layer ถัดไปจะได้ input ≈ 0.98 ทำให้ z ยิ่งใหญ่ขึ้น)

  3. หาความชัน \(g'(z)\) ของ tanh (จาก Lesson 3 §5: \(g' = 1 - \tanh^2 z\))
    $$g'(2.25) = 1 - 0.978^2 = 0.0435$$
  4. ตัวคูณ backprop ต่อ 1 layer ≈ (weight) × g′
    $$0.5 \times 0.0435 \approx 0.0217$$
  5. คูณข้าม 5 layer (chain rule ของ Lesson 5 §1)
    $$0.0217^{5} \approx 4.8 \times 10^{-9}$$

gradient ที่ไปถึง layer แรกสุดเหลือระดับ \(10^{-9}\) เทียบกับตอนเริ่ม ⇒ weight ของ layer ล่างแทบไม่ถูกอัปเดต (ตัวเลข 0.9 กับ 0.5 เป็นสมมติเพื่อดูกลไก แต่ข้อสรุปเชิงขนาดไม่เปลี่ยน).

ทางแก้ 1 — ReLU + He: เปลี่ยน tanh เป็น relu (ความชัน = 1 เมื่อ \(z > 0\) ไม่อิ่มตัว) และเปลี่ยน initializer เป็น he_normal (variance \(2/n_{in}\) จาก Lesson 5 §2). ผลที่เห็นในแผง histogram ด้านบน: bias ของทุก layer "บานออก" จนช่วงอ่านได้ประมาณ ±0.1 ถึง ±0.2 ภายใน 20 epoch = weight กำลังเรียนรู้จริง.

ทางแก้ 2 (ตัวอย่างกรณีตรงข้าม) — learning rate เล็กเกิน: แผงล่างขวาใช้ SGD lr = 0.0001: แกนของ bias เหลือระดับ 2×10⁻⁴ ถึง 4×10⁻⁴ (เล็กกว่าแผงบนประมาณ 500 เท่า — สไลด์ไม่ได้ระบุ lr ของแผงบน จึงเทียบได้แค่ขนาดคร่าวๆ) และแถบ kernel เป็นแนวราบตลอด 20 epoch — เพราะการอัปเดตต่อก้าวคือ \(\Delta\theta = -\alpha\,\nabla J\) ยิ่ง \(\alpha\) เล็ก weight ยิ่งแทบไม่ขยับ. อาการ "กราฟแบนราบ" จึงมีอย่างน้อยสองสาเหตุที่ต้องแยก: gradient เล็ก (vanishing) กับ learning rate เล็ก.

สไลด์ระบุ 3 อาการที่บอกว่ากำลังเจอ exploding gradient ตารางนี้จับคู่แต่ละอาการกับสิ่งที่จะเห็นจริงในกราฟ/log และสิ่งที่ควรสงสัยก่อน:

อาการ (สไลด์)สิ่งที่เห็นในกราฟ/logควรสงสัยอะไร
โมเดลไม่ "จับ" ข้อมูล train (loss แย่)loss ค้างสูง ไม่ลดlearning rate, init, vanishing
ไม่เสถียร loss กระโดดใหญ่ระหว่างการอัปเดตloss ขึ้นๆ ลงๆ แรงๆlearning rate ใหญ่เกิน, gradient ใหญ่
loss กลายเป็น NaNloss: nanexploding เต็มที่ (weight ล้นเป็น ∞)

ตัวอย่างที่สอนในคาบ: โมเดล ReLU+He เดิมแต่เพิ่ม learning rate เป็น 0.2 (momentum 0.9) — val_accuracy ค้างประมาณ 0.5 (เท่าเดา) และ loss แกว่งรอบ 0.69 ซึ่งใกล้ \(\ln 2 \approx 0.693\) (ค่า cross-entropy ของโมเดลที่ทำนาย 0.5 ทุกตัวอย่าง — Lesson 1). ทางแก้: ลด learning rate, gradient clipping (Lesson 5 §1) หรือ Batch Normalization.

คำนวณ: Batch Normalization "ดึงกลับ" ค่าที่ใหญ่เกินอย่างไร (สไลด์หน้า 18)
กำหนด: z ของ 1 neuron ใน mini-batch 4 ตัวอย่าง = 2, 4, 6, 8 ; \(\gamma = 1,\ \beta = 0\) (ละ \(\epsilon\)) — สูตรจาก Lesson 5 §3
  1. ค่าเฉลี่ยของ batch
    $$\mu = \frac{2+4+6+8}{4} = 5$$
  2. variance ของ batch
    $$\sigma^2 = \frac{(2-5)^2 + (4-5)^2 + (6-5)^2 + (8-5)^2}{4} = \frac{9+1+1+9}{4} = 5$$
  3. normalize: \(\hat z = (z-\mu)/\sqrt{\sigma^2}\)
    $$\hat z = \frac{-3}{\sqrt5},\ \frac{-1}{\sqrt5},\ \frac{1}{\sqrt5},\ \frac{3}{\sqrt5} = -1.342,\ -0.447,\ 0.447,\ 1.342$$

ไม่ว่า z เดิมจะใหญ่แค่ไหน (เช่นถ้าเป็น 200, 400, 600, 800 ก็ได้ \(\hat z\) ชุดเดิมเป๊ะ) ค่าที่ส่งเข้า activation ถัดไปคงอยู่ราว ±1.3 เสมอ ⇒ ไม่ระเบิด และไม่ตกไปอยู่ในโซน saturation ของ tanh/sigmoid.

8. Hyperparameter Tuning: มีอะไรให้ปรับ และค่าเริ่มต้นที่ควรใช้

สไลด์หน้า 19 ตั้งต้นด้วยหลักการ: hyperparameter เหมือนปุ่มหมุนที่ต้องจูนเพื่อให้ได้ผลดีที่สุด และเพราะในโมเดลลึกการจูนด้วยมือช้าและมักไม่ดีที่สุด การจูนแบบอัตโนมัติจึงคุ้มกว่า.

สไลด์แบ่ง hyperparameter เป็น 3 หมวด แต่ละหมวดตอบคำถามต่างกัน:

หมวดตอบคำถามว่าตัวอย่าง

Learning & optimizationโมเดลเรียนรู้ "อย่างไร"learning rate/schedule, batch size, optimizer, init, BN, epochs
Avoid overfittingป้องกันจำข้อสอบเก่าL2 (\(\lambda\)), dropout rate, data augmentation

สไลด์หน้า 21–23 ให้ "สูตรลัด" ที่ไม่ต้องค้นหาเลยในหลายเรื่อง — ตารางด้านล่างสรุปว่าไม่ต้องจูนตัวไหน และต้องจูนตัวไหน:

สไลด์: ถ้ามีความจุมากเกิน (layer/unit เยอะ) โมเดลอาจจำ training set — ลองเทียบ input 10,000 ตัว (เช่น multi-hot ของคำใน IMDB) กับ 1 hidden layer และ output 1 unit; สูตร Dense: \(n_{in}n_{out}+n_{out}\)
  1. hidden 128 unit
    $$(10000\times128 + 128) + (128\times1+1) = 1{,}280{,}128 + 129 = 1{,}280{,}257$$
  2. hidden 32 unit
    $$(10000\times32 + 32) + (32\times1+1) = 320{,}032 + 33 = 320{,}065$$
  3. เทียบ
    $$\frac{1{,}280{,}257}{320{,}065} \approx 4.0$$

เพิ่ม hidden จาก 32 เป็น 128 (×4) ทำให้พารามิเตอร์เพิ่ม ×4 เกือบพอดี เพราะ layer แรกที่คูณกับ input 10,000 ครองเกือบทั้งหมด. ถ้าข้อมูล train มีแค่ 25,000 ตัวอย่าง พารามิเตอร์ 1.28 ล้านตัวเป็นตัวการให้ overfit ได้ง่าย — นี่คือเหตุผลที่สไลด์บอกให้ "ลดจำนวน hidden unit หรือใช้วิธีลด overfitting" เมื่อเห็นอาการ.

สไลด์หน้า 24 สรุปขั้นตอนมาตรฐานของการจูน 4 ขั้น (นำไปใช้ใน §10): (1) ระบุ hyperparameter และช่วงค้นหา → (2) สร้างโมเดลที่รับค่าเหล่านั้น → (3) เลือกอัลกอริทึมค้นหา → (4) เซฟโมเดลที่ดีที่สุดแล้ววัดผลบน test set.

9. อัลกอริทึมค้นหา: Grid, Random, HyperBand, Bayesian

อ่านรูป (Grid Layout): แกนนอนคือพารามิเตอร์ที่ "สำคัญ" (มีผลต่อคะแนนมาก — เส้นโค้งสีเขียวด้านบนคือคะแนนที่แกนนี้) ส่วนแกนตั้งคือพารามิเตอร์ที่ "ไม่สำคัญ". จุด 9 จุดเรียงเป็น 3 แถว × 3 คอลัมน์ ⇒ แม้ลองทั้งหมด 9 ครั้ง ค่าของพารามิเตอร์สำคัญที่ถูกทดสอบมีแค่ 3 ค่าไม่ซ้ำกัน (แถวที่เหลือทดสอบค่าเดิมซ้ำ แค่ไปเปลี่ยนพารามิเตอร์ที่ไม่สำคัญ).

คำนวณ: Grid Search ต้องเทรนกี่ครั้งสำหรับ search space ในสไลด์หน้า 29
พื้นที่ค้นหา (จากโค้ดสไลด์): num_layers ∈ {1, 2}; units_i ∈ [10, 50] step 1 = 41 ค่า/layer; activation ∈ {relu, elu, selu} (3 ค่า ใช้ร่วมกัน); dropout_i ∈ {0, 0.1, …, 0.5} = 6 ค่า/layer; lr ต่อเนื่อง — สมมติตาราง 5 ค่า
  1. กรณี 1 layer
    $$41 \times 3 \times 6 = 738$$
  2. กรณี 2 layer (units และ dropout มี 2 ชุด)
    $$41^2 \times 3 \times 6^2 = 1681 \times 3 \times 36 = 181{,}548$$
  3. รวม แล้วคูณจำนวนค่า lr
    $$(738 + 181{,}548) \times 5 = 911{,}430$$

~ 911,430 ครั้งของการเทรน (ถ้าครั้งละ 1 นาทีก็เกือบ 1.7 ปี) — ในสไลด์หน้า 31 การค้นด้วย Hyperband ใช้เพียง 211 trial ใช้เวลา 43 นาที 46 วินาที. นี่คือความหมายของ "computationally expensive" ที่สไลด์บอก: จำนวนชุดโตแบบคูณตามจำนวนตัวเลือกทุกตัว.

ใช้งบ 9 ครั้งเท่ากัน แต่ Random Layout ทดสอบพารามิเตอร์สำคัญที่ 9 ค่าไม่ซ้ำกัน (เทียบกับ Grid ที่ได้ 3 ค่า) — จึงมีโอกาสใกล้ค่าที่ดีที่สุดมากกว่ามาก นี่คือความหมายของ "fewer, more diverse combinations" ในสไลด์. ข้อเสียที่สไลด์ระบุ: มันเป็น blind search คือไม่ใช้ผลของ trial ก่อนหน้าเลย อาจพลาดย่านที่ดี.

ไอเดีย: ให้ทุก configuration ลองเทรนด้วยงบน้อย (เช่น 1 epoch) ก่อน — ตัวที่แย่ตั้งแต่ต้นมักแย่ต่อไป จึงตัดทิ้ง เก็บเฉพาะตัวที่ดี (ตัวละ 1/η) แล้วเพิ่มงบ η เท่า ให้ตัวรอด ทำซ้ำจนเหลือตัวเดียวที่ได้งบเต็ม. สูตรของ bracket ที่ให้ \(n\) = จำนวนเริ่มต้น, \(r\) = งบเริ่มต้น, \(\eta\) = ตัวคูณ:

$$n_i = \left\lfloor n\,\eta^{-i} \right\rfloor,\qquad r_i = r\,\eta^{\,i}$$
คำนวณ: bracket \(s=4\) ของตารางในสไลด์ (max_iter = 81, \(\eta = 3\), \(n = 81\), \(r = 1\))
  1. หา \((n_i, r_i)\) ทีละรอบ \(i = 0..4\)
    $$\begin{aligned} i=0:&\; n_0 = 81,\; r_0 = 1\\ i=1:&\; n_1 = \lfloor 81/3 \rfloor = 27,\; r_1 = 1\cdot3 = 3\\ i=2:&\; n_2 = 9,\; r_2 = 9\\ i=3:&\; n_3 = 3,\; r_3 = 27\\ i=4:&\; n_4 = 1,\; r_4 = 81 \end{aligned}$$

    ตรงกับคอลัมน์ \(s=4\) ของตาราง

  2. คิดต้นทุนของแต่ละรอบ = \(n_i \times r_i\)
    $$81\times1 = 81,\quad 27\times3 = 81,\quad 9\times9 = 81,\quad 3\times27 = 81,\quad 1\times81 = 81$$

    ทุกรอบใช้งบเท่ากัน 81 ⇒ ทั้ง bracket = \(5\times81 = 405\) epoch

  3. เทียบกับการเทรนทุก configuration ให้เต็ม
    $$81 \times 81 = 6561 \text{ epoch}$$ $$\frac{6561}{405} \approx 16.2$$

ค้นหา 81 configuration ด้วยงบ 405 epoch แทน 6,561 (ถูกกว่าราว 16 เท่า) เพราะ configuration ที่แย่ถูกตัดตั้งแต่ใช้ไปแค่ 1–3 epoch. ใน KerasTuner (สไลด์หน้า 30) พารามิเตอร์ max_epochs=81, factor=3 คือ \(\text{max\_iter}=81,\ \eta=3\) ตัวเดียวกันนี้.

ไอเดีย: ทุกครั้งที่ลอง ได้คู่ (hyperparameter → คะแนน) เพิ่มอีก 1 จุด. Surrogate model (Gaussian Process ตามตำนานรูป) เรียนรู้จากจุดที่มีแล้วบอกว่า "ที่ค่า \(x\) นี้ คาดว่าคะแนนเฉลี่ย \(\mu(x)\) และไม่แน่ใจเท่าไร \(\sigma(x)\)". จากนั้น acquisition function แบบ UCB ให้คะแนนจุดที่จะลองต่อไป:

$$\text{UCB}_\lambda(x) = \mu(x) + \lambda\,\sigma(x)$$

คะแนนที่คาดไว้ + โบนัสให้จุดที่ยังไม่ค่อยรู้ (ยิ่งไม่แน่ใจ ยิ่งได้โบนัสมาก); \(\lambda\) คือตัวปรับว่าให้โบนัสมากแค่ไหน

คำนวณ: λ ตัดสินใจว่าจะ "ขุดจุดเดิม" หรือ "สำรวจจุดใหม่"
มี 2 candidate: A (เคยลองใกล้ๆ แล้ว) \(\mu = 0.85,\ \sigma = 0.02\)  |  B (ยังไม่เคยลองแถวนี้) \(\mu = 0.80,\ \sigma = 0.20\)
  1. \(\lambda = 0.2\) (เน้น exploit)
    $$\text{UCB}(A) = 0.85 + 0.2(0.02) = 0.854,\qquad \text{UCB}(B) = 0.80 + 0.2(0.20) = 0.840$$

    A สูงกว่า ⇒ ลอง A (ตามความคาดหวังเฉลี่ย)

  2. \(\lambda = 1.2\) (เน้น explore)
    $$\text{UCB}(A) = 0.85 + 1.2(0.02) = 0.874,\qquad \text{UCB}(B) = 0.80 + 1.2(0.20) = 1.040$$

    B สูงกว่ามาก ⇒ ลอง B (ย่านที่ยังไม่รู้)

ค่าเฉลี่ยต่ำกว่า (B: 0.80) ก็ถูกเลือกได้ ถ้า λ ใหญ่พอให้โบนัสความไม่แน่ใจชนะ — ตรงกับรูป λ = 5 ในสไลด์ที่เส้นน้ำเงิน (acquisition) พุ่งสูงในย่านที่ไม่มีจุดข้อมูล.

10. ใช้ KerasTuner: สร้าง HyperModel → เลือก Tuner → ค้นหา → ดึงผล

แนวคิด: แทนที่จะเขียน Dense(32, ...) ด้วยตัวเลขตายตัว ให้เขียน Dense(hp.Int("units", 10, 50)) — "ช่อง" ที่ tuner จะมาเติมค่าเอง. ประเภทของช่อง:

ฟังก์ชันความหมายตัวอย่างในสไลด์
hp.Int(name, min, max, step)จำนวนเต็มในช่วงnum_layers 1–2; units 10–50
hp.Float(name, min, max, step / sampling)ทศนิยมในช่วงdropout 0–0.5 step 0.1; lr 1e-4–1e-2 แบบ log
hp.Choice(name, values)เลือก 1 จากรายการactivation ∈ {relu, elu, selu}
hp.Boolean(name)จริง/เท็จใช้ dropout หรือไม่
คำนวณ: ทำไม learning rate ต้องสุ่มแบบ sampling='log'
ช่วงค้นหา 0.0001 ถึง 0.01 (กว้าง 2 "ระดับ" คือ \(10^{-4}\!\to\!10^{-3}\) และ \(10^{-3}\!\to\!10^{-2}\)) — อยากรู้ว่าสุ่มแล้วได้ค่าต่ำกว่า 0.001 กี่ %
  1. สุ่มแบบเส้นตรง (uniform)
    $$P(\text{lr} < 0.001) = \frac{0.001 - 0.0001}{0.01 - 0.0001} = \frac{0.0009}{0.0099} \approx 9.1\%$$

    ค่าเกือบทั้งหมดจะไปกองแถว 0.001–0.01

  2. สุ่มแบบ log (uniform บน \(\log_{10}\))
    $$P(\text{lr} < 0.001) = \frac{\log_{10}0.001 - \log_{10}0.0001}{\log_{10}0.01 - \log_{10}0.0001} = \frac{-3-(-4)}{-2-(-4)} = \frac{1}{2} = 50\%$$

แบบ log ให้ความน่าจะเป็นเท่ากันทุก "ระดับ" (\(10^{-4}\!\sim\!10^{-3}\) เท่ากับ \(10^{-3}\!\sim\!10^{-2}\)) — เหมาะกับ learning rate ที่สิ่งสำคัญคือขนาดหลัก (เลขชี้กำลัง) ไม่ใช่ผลต่างเชิงเส้น.

อ่าน search_space_summary() ในสไลด์: "Default search space size: 5" — ทั้งที่โค้ดมี units_i และ dropout_i ให้ layer ที่ 2 ด้วย แต่ tuner เห็น units_0, dropout_0 เท่านั้น เพราะ hyperparameter ถูกสร้างตอนที่โค้ดรันผ่านบรรทัดนั้นจริงๆ — units_1/dropout_1 จะโผล่มาเมื่อ tuner สุ่มได้ num_layers = 2 (hyperparameter แบบมีเงื่อนไข). 4 ตัวเลือก tuner คือ 4 อัลกอริทึมของ §9 โดยส่ง build_model เข้าไปเหมือนกัน เปลี่ยนแค่ชื่อคลาส (kt.RandomSearch, kt.Hyperband, kt.BayesianOptimization, …).

ทำไมต้องมี
การแยก "build_model(hp)" ออกจาก "อัลกอริทึมค้นหา" ทำให้เปลี่ยนวิธีค้น (Random → Hyperband → Bayesian) ได้โดยไม่แตะโค้ดโมเดล และเรียก callbacks=[early_stopping_cb] ในทุก trial ให้แต่ละ trial ไม่เสียเวลาเทรนเกินจำเป็น (เชื่อม §2).
เปลี่ยนแล้วเกิดอะไร
ถ้าเปลี่ยน objective จาก val_accuracy เป็น val_loss ทิศทางกลับ (ต้องต่ำสุด แทนสูงสุด) และโมเดลที่ "ดีที่สุด" อาจเป็นคนละตัว (accuracy กับ loss ไม่จำเป็นต้องเห็นตรงกัน). ถ้าใช้ test set ตัดสินใจระหว่างค้น จะทำให้ตัวเลข test กลายเป็น optimistic เหมือน validation (data leakage).

11. ข้อควรระวังและแนวทางปฏิบัติ (สไลด์หน้า 32)

สไลด์สรุปไว้ 3 ข้อ (หน้า 32) ซึ่งทั้งหมดผูกกับสิ่งที่คำนวณมาแล้ว:

  1. ไม่มีตัวเลขวิเศษ — ค่าที่ดีขึ้นกับ dataset และ task จึงต้องรู้ว่าแต่ละ hyperparameter ทำอะไร (ตาราง §8) และยังต้องใช้ domain knowledge อ่านผลการค้น
  2. อย่าลองทีละค่าด้วยมือ — ใช้ tuner (§9–10); ตั้งค่า global config ให้ hyperparameter ที่ไม่ได้จูน
  3. Coarse-to-fine — ถ้าช้า ให้ค้นแบบหยาบก่อน ดูทิศทาง แล้วค่อยค้นละเอียดในช่วงที่ดี
ตัวอย่าง coarse-to-fine กับ learning rate
  1. รอบหยาบ: ช่วง \([10^{-4},\,10^{-2}]\) แบบ log (ตัวอย่างใน §10)

    สมมติผลออกมา learning rate ที่ดีที่สุดอยู่แถว 0.0006 และคะแนนของค่าอื่นๆ ตกลงห่างจากแถบนี้

  2. รอบละเอียด: ตีกรอบใหม่แคบลง เช่น \([2\times10^{-4},\,10^{-3}]\)

    ช่วงเดิมกว้าง \(\log_{10}(100) = 2\) ระดับ ช่วงใหม่กว้าง \(\log_{10}(5) \approx 0.7\) ระดับ ⇒ พื้นที่ค้นหาเล็กลงราว \(2/0.7 \approx 2.9\) เท่า และทุก trial ตกในย่านที่มีแนวโน้มดีแล้ว

ในสคริปต์ที่สอนในคาบ ผู้สอนทำแบบนี้จริง: Bayesian รอบแรกได้ learning rate ≈ 0.000624 แล้วล็อกไว้ และทดลองต่อกับ weight decay 6 ค่า (0 … 1e-4) ซึ่งให้ val_loss ต่างกันเพียง 0.2657–0.2687 (ต่างกัน < 0.01) — สัญญาณว่าตัวนั้นไม่ใช่ปุ่มสำคัญ ไม่ควรเสียเวลาค้นละเอียดกว่านี้.
