ก่อนเริ่ม — 3 คำที่ต้องแยกให้ออก
  • Epoch = เทรนวนครบข้อมูล train ทั้งชุด 1 รอบ
  • Batch (หรือ step) = ข้อมูลกลุ่มเล็กๆ ที่ใช้อัปเดต weight 1 ครั้ง. จำนวน batch ต่อ epoch = \(\lceil m / B \rceil\) เมื่อ \(m\) = จำนวนตัวอย่าง train, \(B\) = batch size (เครื่องหมาย \(\lceil\ \rceil\) คือ "ปัดขึ้น")
  • Hyperparameter = ค่าที่เราตั้งเองก่อนเทรน (learning rate, จำนวน layer, dropout rate …) ต่างจาก parameter \(\theta\) (weight/bias) ที่โมเดลเรียนรู้เองจากข้อมูล
ต้องรู้ก่อน — "loop ซ้อน loop" ของ model.fit()

ทุกอย่างในบทนี้วางอยู่บนภาพเดียว: model.fit() คือ loop ซ้อน loop. ถ้าเขียนเป็นภาษาคนจะได้แบบนี้:

  1. เริ่มการเทรน (ครั้งเดียว)
  2. สำหรับ epoch = 1, 2, …, E:
    1. สำหรับ batch = 1, 2, …, \(\lceil m/B \rceil\): หยิบข้อมูล \(B\) แถว → forward → คำนวณ loss → backprop → อัปเดต weight 1 ครั้ง
    2. จบ epoch แล้ว: ถ้ามี validation data ก็เอา validation ทั้งชุดมาทดสอบ (ไม่อัปเดต weight) ได้ val_loss, val_accuracy
  3. จบการเทรน (ครั้งเดียว)

ตัวอย่างเป็นตัวเลข: ข้อมูล train 150 แถว, batch_size=64 ⇒ \(\lceil 150/64 \rceil = \lceil 2.34 \rceil = 3\) batch ต่อ epoch. batch แรกได้ 64 แถว, batch สองได้ 64 แถว, batch สามได้ 22 แถวที่เหลือ (batch สุดท้ายเล็กกว่าเพื่อนได้ ไม่ผิด). ถ้าเทรน 50 epoch ก็คือ weight ถูกอัปเดต \(50 \times 3 = 150\) ครั้ง.

ตัวเลข 150 / 64 / 3 ชุดนี้จะตามเราไปทั้งบท เพราะ dataset ที่อาจารย์ใช้สาธิต (circle.csv) มี train 150 แถว, validation 50 แถว, test 50 แถวพอดี.

1. Callback คืออะไร: "ผู้ช่วยข้างสนาม" ที่ Keras เรียกให้เอง

เริ่มจากปัญหาก่อน (ทำไมถึงต้องมีสิ่งนี้): สมมติคุณสั่ง model.fit(X, y, epochs=50) แล้วเดินไปกินข้าว กลับมาเจอสามสถานการณ์นี้ ซึ่งทุกคนที่เทรนโมเดลจริงเคยเจอหมด:

  • "มันดีที่สุดตอน epoch 31 แต่ฉันเทรนไปถึง 50" — val_loss ลดถึงจุดต่ำสุดกลาง ๆ ทาง แล้วค่อยๆ สูงขึ้นเพราะโมเดลเริ่ม overfit. ตอนเทรนจบ weight ที่อยู่ในมือคือของ epoch 50 ซึ่งแย่กว่า epoch 31. ของดีที่สุดผ่านมือไปแล้วแต่เราไม่ได้เก็บ
  • "เทรนไป 4 ชั่วโมง แล้ว Colab ตัดการเชื่อมต่อ" — ไม่มีอะไรอยู่บนดิสก์เลย ต้องเริ่ม epoch 1 ใหม่
  • "อยากลด learning rate ลงครึ่งหนึ่งตอน epoch 20" — แต่ fit() เป็นกล่องดำ เรายื่นมือเข้าไประหว่างทางไม่ได้

ทางแก้แบบดิบๆ คือเลิกใช้ model.fit() แล้วเขียน loop เทรนเองทั้งหมด เพื่อจะได้แทรกโค้ดของเราเข้าไประหว่าง epoch ได้ — ซึ่งยาว ผิดง่าย และต้องเขียนใหม่ทุกโปรเจกต์. Keras จึงเสนอทางที่สาม: เปิด "ช่องเสียบ" (hook) ไว้ในจุดสำคัญของ loop แล้วให้เราส่ง object เข้าไปหนึ่งตัว object นั้นจะถูกเรียกให้เองเมื่อถึงแต่ละช่อง. object ตัวนั้นคือ callback.

นิยามที่อาจารย์ทำสีไว้ทั้งประโยคคือหัวใจของหน้านี้: callback คือ an object that is passed to model.fit(). It is called by the model at various stages during training และสามารถ specific actions เช่นหยุดเทรนก่อนกำหนด, เซฟโมเดล, หรือปรับ learning rate. แยกคำสำคัญสามคำให้ชัด: (ก) มันเป็น object ไม่ใช่ฟังก์ชันลอยๆ — เราสร้างจาก class แล้วส่ง instance เข้าไป; (ข) called by the model แปลว่าเราไม่เคยเรียกเมธอดพวกนี้เอง Keras เรียกให้; (ค) various stages แปลว่ามีหลายจุดเวลาให้เลือกเสียบ ไม่ใช่จุดเดียว.

คอลัมน์ซ้ายของสไลด์ไล่ชื่อ "ช่องเสียบ" ทั้งหมดที่ Base Callback class มีให้ ซึ่งจับคู่กันเป็น begin/end เสมอ และแยกตามสามโหมดของโมเดล:

โหมดเมธอดที่เรียกได้ (จากสไลด์หน้า 1)ถูกเรียกเมื่อ
เทรน (fit)on_train_begin, on_train_endเริ่ม/จบการเทรนทั้งหมด — อย่างละ 1 ครั้ง
เทรน (fit)on_epoch_begin, on_epoch_endเริ่ม/จบแต่ละ epoch — epoch ละครั้ง
เทรน (fit)on_train_batch_begin, on_train_batch_end, on_batch_begin, on_batch_endเริ่ม/จบแต่ละ batch ของการเทรน
ประเมิน (evaluate / validation)on_test_begin, on_test_end, on_test_batch_begin, on_test_batch_endตอน evaluate() และตอนคำนวณ validation ท้าย epoch
ทำนาย (predict)on_predict_begin, on_predict_end, on_predict_batch_begin, on_predict_batch_endตอน predict()

จุดที่ข้อสอบชอบหลอกคือคำว่า test: hook ชื่อ on_test_* ไม่ได้หมายถึง test set ของเราเสมอไป — มันหมายถึง "โหมดประเมินผลโดยไม่อัปเดต weight" ซึ่งเกิดขึ้นทุกครั้งที่จบ epoch ถ้าเราส่ง validation_data เข้าไป. ในสคริปต์ที่อาจารย์รันในคาบ callback ที่ดัก on_test_batch_end พิมพ์ออกมา 2 บรรทัดต่อ epoch เพราะ validation มี 50 แถวและ batch ของการประเมินเป็น 32 ⇒ \(\lceil 50/32 \rceil = 2\).

คราวนี้มาดูโค้ดที่สไลด์เขียนไว้ — มันคือการสร้าง callback ของตัวเองจาก base class โดยเลือกเสียบแค่ 3 ช่อง:

from keras.callbacks import Callback

class my_callback(Callback):
    # Called at the beginning of training.
    def on_train_begin(self, logs):
        print("training start")

    # Called at the beginning of a training batch
    def on_train_batch_end(self, batch, logs):
        print(f"End of batch:{batch+1}")

    # Called at the end of an epoch.
    def on_epoch_end(self, epoch, logs):
        print(f"End of epoch:{epoch+1}")

history = model.fit(X, y, validation_data=(Xval, yval), epochs=50,
                    batch_size=64, callbacks=[my_callback()])

validation_data=(Xval, yval)ให้ Keras ประเมินหลังจบทุก epoch ⇒ logs ของ on_epoch_end จะมี val_loss/val_accuracy เพิ่มมาด้วย

ตารางนี้อธิบายกฎเหล็กข้อหนึ่งที่จะใช้ทั้งบท: callback ใดๆ ที่ตัดสินใจจาก val_loss (EarlyStopping, ReduceLROnPlateau, ModelCheckpoint แบบ save_best_only) ทำงานได้เฉพาะที่จังหวะจบ epoch เท่านั้น เพราะระดับ batch ไม่มีค่า validation ให้ดู.

คำนวณ: callback ถูกเรียกกี่ครั้ง และพิมพ์กี่บรรทัด
ให้ \(m = 150\) (train), \(B = 64\), epochs = 3, ใช้ callback ข้างบน
  1. ขั้นที่ 1 — หาจำนวน batch ต่อ epoch
    $$\text{batches} = \left\lceil \frac{150}{64} \right\rceil = \lceil 2.34 \rceil = 3$$

    ต้องปัดขึ้นเพราะเศษ 22 แถวสุดท้ายก็ยังต้องเทรน จะทิ้งไม่ได้

  2. ขั้นที่ 2 — นับการเรียกแต่ละ hook

    on_train_begin: 1 ครั้ง (ต้นการเทรนเท่านั้น)

    on_train_batch_end: \(3 \text{ batch} \times 3 \text{ epoch} = 9\) ครั้ง

    on_epoch_end: 3 ครั้ง

  3. ขั้นที่ 3 — รวมบรรทัดที่พิมพ์
    $$1 + 9 + 3 = 13$$

13 บรรทัด. ถ้าเปลี่ยน batch_size เป็น 32 จะได้ \(\lceil 150/32 \rceil = 5\) batch/epoch ⇒ \(1 + 15 + 3 = 19\) บรรทัด — สังเกตว่า batch size เล็กลง = callback ระดับ batch ถูกเรียกถี่ขึ้น ซึ่งเป็นเหตุผลที่ TensorBoard ตั้ง update_freq='epoch' เป็นค่าเริ่มต้น (ดู §6) ไม่งั้นไฟล์ log จะบวมมาก.

ข่าวดีคือของที่ต้องใช้บ่อยมีให้สำเร็จรูปแล้ว ไม่ต้องเขียน class เอง. อาจารย์ทำสีคำกริยาของแต่ละตัวไว้ ซึ่งก็คือ "หน้าที่" ของมันในหนึ่งคำ — ท่องคู่กริยา-ชื่อคลาสนี้ไว้ เพราะข้อสอบชอบสลับ:

  • EarlyStopping — Interrupting training when the metrics monitored such as validation loss is no longer improving (ถ้าระบุไว้ ยังเก็บโมเดลที่ดีที่สุดระหว่างเทรนไว้ให้ได้ด้วย). กริยาคือ "ขัดจังหวะ/หยุด" ไม่ใช่ "เซฟ"
  • ModelCheckpoint — Saving the current state of the model at different points during training. กริยาคือ "เซฟ" และคำว่า current state บอกว่ามันเซฟสภาพ ณ ตอนนั้น ไม่ได้แปลว่าดีที่สุดโดยอัตโนมัติ
  • BackupAndRestore — Back up and restore the training state. ต่างจากตัวบนตรงคำว่า training state (สภาพการเทรน = weight + เลข epoch + optimizer) ไม่ใช่แค่ตัวโมเดล และมันมีหน้าที่ "เอากลับคืนมา" ด้วย
  • LearningRateScheduler / ReduceLROnPlateau — Dynamically adjusting the value of the learning rate of the optimizer during training. คำว่า dynamically = เปลี่ยนระหว่างทาง ไม่ใช่ตั้งครั้งเดียวตอน compile
  • CSVLogger — Logging training and validation metrics during training. แค่ "จด" ลงไฟล์ ไม่ตัดสินใจอะไรเลย
  • TensorBoard — Visualizing training info. learned by the model during training. แค่ "เขียน log ให้โปรแกรมดูกราฟไปอ่าน" ไม่ได้เปลี่ยนการเทรน

คอลัมน์ขวาของสไลด์ยังไล่ callback ทั้งหมดที่ Keras มี ซึ่งมีตัวที่ไม่ได้สอนละเอียดแต่ควรรู้จักชื่อ: Base Callback class, ModelCheckpoint, BackupAndRestore, TensorBoard, EarlyStopping, LearningRateScheduler, ReduceLROnPlateau, RemoteMonitor (ส่งผลไปเซิร์ฟเวอร์อื่น), LambdaCallback (เขียน callback สั้นๆ จากฟังก์ชันเดียว), TerminateOnNaN (หยุดทันทีเมื่อ loss เป็น NaN — โยงกับอาการ exploding gradient ใน §7), CSVLogger, ProgbarLogger (แถบความคืบหน้าที่เราเห็นตอน fit ก็เป็น callback!), SwapEMAWeights.

ถ้าไม่มี callback การจะ "หยุดตอน validation แย่ลง" หรือ "เซฟตอนดีที่สุด" ต้องเขียน loop เทรนเองทั้งหมด. Callback ให้จุดเสียบที่ Keras เรียกให้ ทำให้พฤติกรรมพวกนี้กลายเป็นโค้ดบรรทัดเดียวที่ต่อเข้าไปได้ และประกอบกันได้ — เอาหลายตัวมาใช้พร้อมกันโดยไม่ต้องแก้โค้ดโมเดล.

ถ้าใส่หลายตัวใน list callbacks=[a, b] ทุกตัวถูกเรียกที่จุดเดียวกันตามลำดับใน list. ถ้าลืมวงเล็บเขียน callbacks=[my_callback] (ส่ง class ไม่ใช่ object) จะ error; ถ้าลืม list เขียน callbacks=my_callback() Keras รุ่นใหม่ยอมรับได้แต่เป็นสไตล์ที่ไม่ควรใช้.
เชื่อมกับ
Early stopping ที่ Lesson 4 อธิบายเป็นหลักการ (หยุดก่อน overfit) ที่นี่กลายเป็น callback จริง; และ "จำนวน batch ต่อ epoch" คือตัวเลขเดียวกับที่ Lesson 5 คำนวณตอนอ่าน progress bar ของ Keras.
ออกสอบสูง — ข้อความที่อาจารย์ทำสี
  • an object — callback เป็น object ที่ส่งเข้า model.fit() ไม่ใช่ argument ตัวเลขหรือฟังก์ชันเปล่าๆ. กับดัก: ตัวเลือกที่บอกว่า "เป็นฟังก์ชันที่เราเรียกเองหลังเทรนจบ"
  • called by the model — โมเดล เป็นฝ่ายเรียก เราไม่ได้เรียก. กับดัก: "ผู้ใช้ต้องเรียก callback เองทุก epoch"
  • various stages during training — มีหลายจังหวะ (เริ่มเทรน / เริ่ม-จบ epoch / เริ่ม-จบ batch / ประเมิน / ทำนาย). กับดัก: "ถูกเรียกเฉพาะตอนจบการเทรน"
  • Interrupting training + no longer improving — คู่คำของ EarlyStopping. กับดัก: สลับไปเป็นหน้าที่ของ ModelCheckpoint
  • Saving the current state of the model — ModelCheckpoint เซฟ "สภาพปัจจุบัน" ไม่ใช่ "สภาพที่ดีที่สุด" (ถ้าไม่สั่ง save_best_only)
  • Back up / restore the training state — BackupAndRestore. คำชี้ขาดคือ training state (มีเลข epoch ด้วย) ไม่ใช่แค่ weight. กับดัก: เอาไปตอบว่าใช้เก็บโมเดลที่ดีที่สุด
  • Dynamically adjusting the learning rate — LearningRateScheduler/ReduceLROnPlateau. กับดัก: บอกว่าปรับ "weight" หรือปรับ "batch size"
  • Logging + metrics — CSVLogger เขียนตัวเลขลงไฟล์เฉยๆ ไม่มีผลต่อการเทรน
  • Visualizing training info. — TensorBoard. กับดัก: บอกว่า TensorBoard "ปรับ learning rate ให้อัตโนมัติ"

2. EarlyStopping: หยุดเมื่อไม่ดีขึ้นตามเกณฑ์ที่กำหนด

ปัญหาก่อน: เราตั้ง epochs=50 เพราะเดาว่า "น่าจะพอ" แต่ความจริงคือกราฟ val_loss มักลดลงช่วงแรก แตะจุดต่ำสุดที่ไหนสักแห่ง แล้วค่อยๆ ไต่ขึ้นเพราะโมเดลเริ่มจำ training set (overfit — Lesson 4). เทรนต่อหลังจุดนั้นจึงเป็นการเสียเวลาและทำให้โมเดลแย่ลง. แต่จุดต่ำสุดอยู่ epoch ไหน เราไม่รู้ล่วงหน้า — ต้องให้โปรแกรมเฝ้าดูแทน.

แต่ "แย่ลง" ตัดสินยากกว่าที่คิด เพราะ val_loss ไม่ได้ลดเรียบๆ มันกระเพื่อมขึ้นลงทุก epoch (validation มีแค่ 50 แถว เปลี่ยนไปนิดเดียวก็แกว่ง). ถ้าหยุดทันทีที่แย่ลง 1 ครั้ง เราจะหยุดเพราะ noise. EarlyStopping จึงมี "ปุ่มปรับความอดทน" ให้สองตัว คือ patience (ยอมให้แย่ติดกันได้กี่ครั้ง) และ min_delta (ดีขึ้นเท่าไรถึงจะนับว่าดีขึ้นจริง).

ประโยคที่อาจารย์ทำสีไว้เป็นคำนิยามที่ใช้ตอบข้อสอบได้เลย: EarlyStopping จะ Stop training when the monitored performance metric shows no sufficient improvement ต่อเนื่องเป็นจำนวน epoch ที่กำหนดด้วย patience และเลือกได้ว่าจะให้คืน weight ของ epoch ที่ดีที่สุดกลับมาไหมด้วย restore_best_weights=True. คำที่ต้องอ่านช้าๆ คือ no sufficient improvement — ไม่ใช่ "แย่ลง" เฉยๆ แต่คือ "ดีขึ้นไม่พอตามเกณฑ์" ซึ่งรวมกรณี "ดีขึ้นนิดเดียว" เข้าไปด้วย. นี่คือที่มาของ min_delta.

from tensorflow.keras.callbacks import EarlyStopping

# min_delta can define how much improvement is required
early_stopping_cb = EarlyStopping(monitor='val_loss', patience=5,
                                  min_delta=0.001, restore_best_weights=True)

history = model.fit(X, y, validation_data=(Xval, yval), epochs=50,
                    batch_size=150, callbacks=[early_stopping_cb])

อ่านตารางนี้ให้เป็นคือได้ครึ่งบทแล้ว: คอลัมน์ loss (ของ train) ลดลงเรื่อยๆ ตลอด 0.4030 → 0.2965 ไม่มีสะดุด แต่ val_loss ลงไปแตะก้นที่ 0.4750 ตอน epoch 31 แล้วกลับสูงขึ้นเป็น 0.5149 — นี่คือหน้าตาของ overfitting ที่เห็นด้วยตัวเลข: โมเดลเก่งขึ้นกับข้อมูลที่เคยเห็น แต่แย่ลงกับข้อมูลที่ไม่เคยเห็น. ถ้าเราดูแต่ loss อย่างเดียวจะไม่มีวันรู้ว่าต้องหยุด — เหตุผลที่ monitor ต้องเป็น val_loss ไม่ใช่ loss.

หน้า 4 คืองานที่อาจารย์ทำให้ดูทีละบรรทัดว่ากลไกตัดสินใจอย่างไร และปิดท้ายด้วยหมายเหตุสามดาว: "การจะนับว่าดีขึ้น ต้องลด val_loss ได้อย่างน้อย 0.001 เทียบกับค่าที่ดีที่สุดเท่าที่ผ่านมา". ประโยคท้ายนี้สำคัญกว่าที่เห็น — ลองไล่ตามเองทีละขั้น:

กติกาที่ใช้ตัดสินแต่ละ epoch (เมื่อ monitor เป็นค่าที่ยิ่งน้อยยิ่งดีอย่าง val_loss):

$$\text{improvement}_t = \text{best} - \text{val\_loss}_t \;\ge\; \text{min\_delta}$$

"ค่าดีที่สุดเดิม ลบ ค่าใหม่" ต้องมากกว่าหรือเท่ากับเกณฑ์ ถึงจะนับว่าดีขึ้น

  • ถ้าเป็นจริง → นับเป็น "ดีขึ้น": อัปเดต best ให้เป็นค่าใหม่ และรีเซ็ตตัวนับ patience เป็น 0
  • ถ้าไม่จริง → ตัวนับ patience +1; เมื่อตัวนับแตะ patience ก็หยุดเทรน
คำนวณตามตารางในสไลด์ ทีละ epoch (patience = 5, min_delta = 0.001)
ให้ เริ่มที่ epoch 28: \(\text{val\_loss} = 0.4806\) ⇒ ตั้ง \(\text{best} = 0.4806\), ตัวนับ = 0
  1. ขั้นที่ 1 — Epoch 29: val_loss = 0.4855
    $$0.4806 - 0.4855 = -0.0049 \;<\; 0.001$$

    ติดลบแปลว่าแย่ลงด้วยซ้ำ ⇒ ไม่ผ่านเกณฑ์ ⇒ ตัวนับ = 1 (best ยังเป็น 0.4806)

  2. ขั้นที่ 2 — Epoch 30: val_loss = 0.4763
    $$0.4806 - 0.4763 = 0.0043 \;\ge\; 0.001$$

    ผ่าน ⇒ best = 0.4763 และตัวนับ รีเซ็ตเป็น 0 (ความอดทนกลับมาเต็มถัง)

  3. ขั้นที่ 3 — Epoch 31: val_loss = 0.4750
    $$0.4763 - 0.4750 = 0.0013 \;\ge\; 0.001$$

    ผ่านแบบฉิวเฉียด (เกินเกณฑ์แค่ 0.0003) ⇒ best = 0.4750, ตัวนับ = 0. สังเกตว่าตัวเทียบเปลี่ยนเป็น 0.4763 แล้ว เพราะ best ถูกอัปเดตไปตั้งแต่ขั้นก่อน

  4. ขั้นที่ 4 — Epoch 32 ถึง 35: val_loss = 0.4887, 0.4982, 0.4904, 0.4957
    $$\begin{aligned} 0.4750 - 0.4887 &= -0.0137 \quad\Rightarrow\; \text{ตัวนับ} = 1\\ 0.4750 - 0.4982 &= -0.0232 \quad\Rightarrow\; \text{ตัวนับ} = 2\\ 0.4750 - 0.4904 &= -0.0154 \quad\Rightarrow\; \text{ตัวนับ} = 3\\ 0.4750 - 0.4957 &= -0.0207 \quad\Rightarrow\; \text{ตัวนับ} = 4 \end{aligned}$$

    ทุกบรรทัดเทียบกับ 0.4750 ตัวเดิม เพราะไม่มี best ใหม่เลย. จุดที่หลายคนพลาด: epoch 34 (0.4904) ดีกว่า epoch 33 (0.4982) แต่ตัวนับไม่รีเซ็ต เพราะเทียบกับ best ไม่ใช่เทียบกับ epoch ก่อนหน้า

  5. ขั้นที่ 5 — Epoch 36: val_loss = 0.5149
    $$0.4750 - 0.5149 = -0.0399 \;<\; 0.001 \;\Rightarrow\; \text{ตัวนับ} = 5 = \text{patience}$$

    ครบ ⇒ STOP — ตรงกับช่องสุดท้ายของตารางในสไลด์ที่เขียนว่า "5 → STOP"

หยุดที่ epoch 36 และเพราะตั้ง restore_best_weights=True โมเดลจะถูกย้อน weight กลับไปเป็นของ epoch 31 (val_loss 0.4750). epoch 32–36 ทั้ง 5 รอบคือ "ค่าเวลาที่จ่ายไปเพื่อความมั่นใจว่ามันไม่ดีขึ้นแล้วจริงๆ".

หลักฐานว่าการคืน weight มีผลจริง — สไลด์หน้า 3 ให้ผลการ evaluate สามชุดไว้เทียบ ซึ่งเป็นตัวเลขที่ตอบคำถาม "แล้วมันต่างกันเท่าไร":

    $$0.4806 - 0.4750 = 0.0056$$

patience เล็กลง = จบเร็วขึ้นแต่ยังได้ของดีเท่าเดิม (ถ้าไม่เล็กจนตัดตอนความก้าวหน้าจริง); min_delta ใหญ่เกินไป = มองความก้าวหน้าจริงเป็น noise แล้วหยุดเร็วเกินและได้โมเดลที่แย่กว่า. ค่า default ของ min_delta คือ 0 ซึ่งแปลว่า "ดีขึ้นแม้แต่นิดเดียวก็นับ" — ปลอดภัยที่สุดถ้าไม่แน่ใจ.

ออกสอบสูง — ข้อความที่อาจารย์ทำสี
  • Stop training — EarlyStopping หยุดการเทรน ไม่ได้ทำอย่างอื่น. กับดัก: ตัวเลือกที่บอกว่ามัน "เซฟไฟล์โมเดลที่ดีที่สุดลงดิสก์ให้" (นั่นคือ ModelCheckpoint; EarlyStopping เก็บ weight ไว้ในหน่วยความจำเท่านั้น)
  • performance metric — สิ่งที่เฝ้าดูคือ metric ที่เราเลือกผ่าน monitor ไม่ใช่ "loss ของ training set" โดยอัตโนมัติ. กับดัก: ตัวเลือกที่เขียน monitor='loss' แล้วอ้างว่าจับ overfitting ได้
  • no sufficient improvement — "ดีขึ้นไม่พอ" ครอบคลุมทั้งกรณีแย่ลงและกรณีดีขึ้นน้อยกว่า min_delta. กับดัก: นิยามว่า "val_loss เพิ่มขึ้นติดกัน N ครั้ง" ซึ่งตกกรณีที่สอง
  • จุดที่ข้อสอบเติมโค้ดมักถาม: ลำดับและชื่ออาร์กิวเมนต์ EarlyStopping(monitor=..., patience=..., min_delta=..., restore_best_weights=...); ค่า default ของ restore_best_weights คือ False และของ min_delta คือ 0; ตัวนับ patience รีเซ็ตเมื่อเจอ best ใหม่ (ไม่ใช่สะสมไปเรื่อยๆ); การเทียบใช้ best ไม่ใช่ epoch ก่อนหน้า

ต้องรู้ก่อน — นับพารามิเตอร์ของ Dense layer

Dense layer หนึ่งชั้นที่รับ input \(n_{in}\) ค่า แล้วให้ output \(n_{out}\) ค่า มีตัวเลขที่ต้องเรียนรู้เท่าไร? ทุก output unit ต้องมีสายเชื่อมไปยังทุก input unit (คนละเส้น คนละน้ำหนัก) บวกด้วย bias อีกตัวละ 1:

$$\#\text{params} = \underbrace{n_{in} \times n_{out}}_{\text{weight (kernel)}} + \underbrace{n_{out}}_{\text{bias}}$$

ลองกับเลขเล็กๆ: input 2 ค่า → output 3 unit. weight = \(2\times3 = 6\) เส้น (จาก \(x_1\) ไป 3 unit, จาก \(x_2\) ไป 3 unit) บวก bias 3 ตัว รวม 9. เช็คด้วยการวาด: unit ที่ 1 ใช้ \(\theta_{11}x_1 + \theta_{12}x_2 + b_1\) = 3 ตัวเลข × 3 unit = 9 ✔

สูตรนี้มาจาก Lesson 2 (รูปแบบ \(z = \Theta a + b\)) — ที่นี่แค่เอามานับจำนวนช่องในเมทริกซ์.

คำนวณ: ทำไม Trainable = 261, Optimizer = 524 และ Total = 785
ให้ โมเดลในสไลด์: input 2 → Hidden1 (10) → Hidden2 (10) → Hidden3 (10) → Output (1), compile ด้วย Adam
  1. ขั้นที่ 1 — นับพารามิเตอร์ทีละ layer ด้วยสูตร \(n_{in}n_{out} + n_{out}\)
    $$\begin{aligned} \text{Hidden1} &= 2\times10 + 10 = 30\\ \text{Hidden2} &= 10\times10 + 10 = 110\\ \text{Hidden3} &= 10\times10 + 10 = 110\\ \text{Output} &= 10\times1 + 1 = 11 \end{aligned}$$

    ตรงกับคอลัมน์ Param # ในสไลด์ (30, 110, 110, 11) เป๊ะ

  2. ขั้นที่ 2 — รวมเป็น Trainable params
    $$30 + 110 + 110 + 11 = 261$$

    นี่คือจำนวนตัวเลขที่ gradient descent ปรับ และเป็นทุกอย่างที่ต้องใช้ตอน predict

  3. ขั้นที่ 3 — Optimizer params ของ Adam

    Adam (Lesson 4) เก็บค่าเฉลี่ยเคลื่อนที่ 2 ชุดต่อทุกพารามิเตอร์ — ชุดหนึ่งของ gradient (\(m\)) อีกชุดของ gradient ยกกำลังสอง (\(v\)):

    $$2 \times 261 = 522$$

    แล้วบวกตัวแปรเดี่ยวอีก 2 ตัว (ตัวนับจำนวน step กับ learning rate)

    $$522 + 2 = 524$$
  4. ขั้นที่ 4 — Total
    $$261 + 524 = 785$$

Total 785 = Trainable 261 + Optimizer 524. ข้อสรุปที่ใช้ตอบข้อสอบ: ตัวเลข Optimizer params จะโผล่มาเฉพาะตอนโหลดไฟล์ .keras ที่เซฟด้วย model.save() เท่านั้น — ถ้าเซฟด้วย save_weights แล้วโหลดกลับ summary() จะขึ้น Total 261 เฉยๆ เพราะไม่มีสถานะ optimizer ติดมา (ผลนี้ยืนยันได้จากสคริปต์ในคาบที่พิมพ์ Total params: 261 หลัง load_weights แต่ Total params: 785 หลัง load_model).

อาร์กิวเมนต์สุดท้ายของ ModelCheckpoint คือ save_freq ซึ่งสไลด์อธิบายว่าควบคุม how often the model is saved: ถ้าใส่ค่า "epoch" (ค่าเริ่มต้น) = เซฟตอนจบทุก epoch; ถ้าใส่จำนวนเต็ม = เซฟทุกๆ N batch ของการเทรน. ความเข้าใจผิดอันดับหนึ่งคือคิดว่า save_freq=6 แปลว่า "ทุก 6 epoch" — ไม่ใช่ มันคือ "ทุก 6 batch" และ batch นับสะสมข้าม epoch.

4. BackupAndRestore: เทรนต่อได้หลังถูกขัดจังหวะ

ปัญหาก่อน: ModelCheckpoint เก็บ "ของดี" ไว้ให้ก็จริง แต่ถ้า Colab ตัดการเชื่อมต่อตอน epoch 27 จาก 50 ไฟล์ที่มีคือ weight ล้วนๆ — เราไม่รู้ว่าเทรนไปถึง epoch ไหนแล้ว, ไม่มี momentum ของ optimizer, และถ้าสั่ง fit ใหม่มันจะเริ่มนับ epoch 1 ใหม่หมด. สิ่งที่ต้องการคือการ "หยุดชั่วคราวแล้วเล่นต่อ" ไม่ใช่ "เก็บผลงาน".

ประโยคที่ทำสีไว้คือคำจำกัดความ: callback นี้ back up and restore the training state after an interruption โดยเซฟ training state ซึ่งสไลด์วงเล็บบอกไว้ว่าประกอบด้วย weights, epoch number และอื่นๆ. คำว่า training state ตรงนี้คือคำที่แยกมันออกจาก ModelCheckpoint ทั้งหมด: ModelCheckpoint เก็บ "ผลงาน" (โมเดลเอาไปใช้งาน) แต่ BackupAndRestore เก็บ "บุ๊กมาร์ก" (เล่มเดิม หน้าเดิม).

ต้องรู้ก่อน — floor, เลขยกกำลัง และ "ฟังก์ชันที่ส่งเป็นอาร์กิวเมนต์"

(1) floor คือการปัดลง เขียนแทนด้วย \(\lfloor\ \rfloor\) — ตัดเศษทิ้งเสมอ ไม่ใช่ปัดใกล้สุด: \(\lfloor 2.9 \rfloor = 2\), \(\lfloor 0.5 \rfloor = 0\), \(\lfloor 3.0 \rfloor = 3\). ใน numpy คือ np.floor.

(2) เลขยกกำลังของเลขน้อยกว่า 1 จะ "หด": \(0.9^0 = 1\) (อะไรยกกำลังศูนย์ก็ได้ 1), \(0.9^1 = 0.9\), \(0.9^2 = 0.81\), \(0.9^3 = 0.729\). ยิ่งเลขชี้กำลังโต ค่ายิ่งเล็กลงแบบทวีคูณ. นี่คือเหตุผลที่คนใช้ \(r^{k}\) เป็น "ตัวลดทอน".

(3) ใน Python ฟังก์ชันเป็น "ค่า" ที่ส่งต่อได้ — เขียน f(3) คือเรียกฟังก์ชัน แต่เขียน f เฉยๆ คือตัวฟังก์ชันเอง. ดังนั้น LearningRateScheduler(lr_function) (ไม่มีวงเล็บหลัง lr_function) คือการยื่น "สูตร" ให้ Keras เก็บไว้ แล้ว Keras จะเป็นคนเรียก lr_function(epoch, lr) เองทุกต้น epoch. ถ้าเผลอเขียน LearningRateScheduler(lr_function()) จะกลายเป็นการเรียกทันทีแล้วส่งผลลัพธ์ (ตัวเลข) ไปแทน ⇒ error.

สไลด์อธิบายกลไกไว้เป็นประโยคเดียว: ที่ต้นของทุก epoch callback จะไปเอา updated learning rate value from schedule function แล้วเอาค่านั้นไปใส่ให้ optimizer. สองคำนี้บอกทุกอย่าง — (ก) updated คือค่าใหม่ ไม่ใช่ค่าเดิม; (ข) มันมาจาก schedule function ที่เราเขียนเอง Keras ไม่ได้คิดสูตรให้. และสไลด์ระบุสเปกของฟังก์ชันนั้นไว้ชัด: รับ epoch index (จำนวนเต็ม เริ่มจาก 0) กับ current learning rate (ทศนิยม) แล้วคืน a new learning rate as output (ทศนิยม). อีกอาร์กิวเมนต์คือ Verbose ซึ่งเป็น int: 0 = เงียบ, 1 = พิมพ์ข้อความบอกทุกครั้งที่เปลี่ยนค่า.

# Define the learning rate schedule function
def lr_function(epoch, lr=0.01, decay_rate=0.9, decay_steps=10000):
    # compute the learning rate for the current epoch
    exp = np.floor((1 + epoch) / decay_steps)
    alpha = lr * (decay_rate ** exp)
    # return the learning rate
    return float(alpha)

$$\alpha_{\text{new}} = \alpha \cdot r^{\left\lfloor \frac{1+e}{s} \right\rfloor}$$

5.2 ReduceLROnPlateau: ลดเมื่อ "ติดแหง็ก" (ไม่ต้องเขียนสูตรเอง)

ข้อเสียของ 5.1 คือเราต้องเดาล่วงหน้าว่าควรลดตอน epoch ไหน ทั้งที่ยังไม่เห็นด้วยซ้ำว่าโมเดลจะติดขัดตรงไหน. ReduceLROnPlateau พลิกตรรกะ: ไม่ลดตามตารางเวลา แต่ลดเมื่อวัดได้ว่าไม่คืบหน้าแล้ว — ใช้เกณฑ์เดียวกับ EarlyStopping เป๊ะ (monitor, patience, min_delta) ต่างกันแค่ว่าเมื่อครบเงื่อนไขแล้ว EarlyStopping "หยุด" ส่วนตัวนี้ "ลด learning rate แล้วไปต่อ".

  2. ขั้นที่ 2 — ติดแหง็กครั้งที่ 2

6. TensorBoard: ดูการเทรนเป็นภาพ

ปัญหาก่อน: สิ่งเดียวที่เราเห็นระหว่างเทรนคือตัวเลขสี่ตัววิ่งผ่านหน้าจอ (loss, accuracy, val_loss, val_accuracy). ถ้าโมเดลเทรนไม่ขึ้น ตัวเลขพวกนี้บอกแค่ว่า "ไม่ขึ้น" แต่ไม่บอกทำไม. คำถามอย่าง "weight ของ layer แรกขยับบ้างไหม" หรือ "การกระจายของ weight เปลี่ยนไปอย่างไรตลอด 20 epoch" ตอบไม่ได้เลยจากตัวเลขสี่ตัวนั้น. TensorBoard คือเครื่องมือที่ทำให้เห็นข้างใน.

อาจารย์นิยาม TensorBoard ว่าเป็น Browser-based application that monitor a variety of information during training. คำว่า browser-based สำคัญกว่าที่คิด: มันไม่ใช่ฟังก์ชัน Python ที่คืนค่ากลับมา แต่เป็นเว็บแอปแยกต่างหาก ที่ไปอ่าน "ไฟล์ log" ที่ Keras เขียนทิ้งไว้ — เพราะงั้นขั้นตอนจึงมีสองฝั่งเสมอ: ฝั่ง Keras เขียน log (ผ่าน callback) กับฝั่งเราเปิดเว็บอ่าน log. สไลด์สรุปสิ่งที่ดูได้ไว้ 4 ข้อ: ดู metric (accuracy, loss) ระหว่างเทรน, ดูการกระจายและ histogram ของ weight กับ bias, ดู computational graph ของโมเดล, และอื่นๆ เช่นสำรวจรูปภาพ. แล้วปิดท้ายว่า Keras ผลิตไฟล์ log พวกนี้ผ่าน TensorBoard callback โดยเรา "แค่ระบุว่าอยากให้เขียน log ไว้ที่ไหน".

from tensorflow.keras.callbacks import TensorBoard

tensorboard_callback = TensorBoard(log_dir='/full path to your log directory')

model.fit(X_train, y_train, epochs=20, validation_split=0.2, callbacks = tensorboard_callback)

อ่านกราฟ loss สองแบบที่สไลด์เอามาเทียบ: แผงที่ชื่อ "Model does not learn anything" มี loss แกว่งอยู่ระหว่างประมาณ 11.0 ถึง 15.0 ตลอดตั้งแต่ step ที่ 400 จนถึง 2,800 โดยค่าเฉลี่ยไม่ลดลงเลย — ขึ้นลงแบบนี้คือ noise ของการสุ่ม batch ไม่ใช่การเรียนรู้. ส่วนแผง "Model learns all the informations" loss เริ่มที่เกิน 25 แล้วดิ่งลงมาราว 10 ภายในประมาณ 1,000 step จากนั้นแบนราบ — รูปตัว L แบบนี้คือหน้าตาปกติของการเรียนรู้ที่สำเร็จ (ลดเร็วตอนต้น แล้วค่อยๆ อิ่มตัว). กฎการวินิจฉัย: ถ้ากราฟของคุณหน้าตาแบบแรก ให้สงสัยสามอย่างตามลำดับ — learning rate (ใหญ่/เล็กเกิน), การ initialize weight, และ vanishing gradient (§7) — ก่อนจะไปโทษว่าข้อมูลไม่พอ.

อ่าน histogram ของ weight/bias: แผง layer1/biases ในสไลด์มีป้ายกำกับเส้นขอบไว้ว่า maximum, 93%, 84%, 69%, median (50%) และ minimum. ความหมายคือแต่ละ epoch (แกนนอนไล่จาก 0 ถึง 1,000 กว่า) เราเอา bias ทั้งหมดใน layer นั้นมาเรียงจากน้อยไปมาก แล้ววาดว่า "ค่ากลางอยู่ตรงไหน (median) และค่าที่กระจายออกไปอยู่แค่ไหน (93%, maximum)". ในภาพนี้แถบเริ่มจากแคบๆ แถว 0.06 แล้วบานออกครอบคลุมช่วงประมาณ 0.06 ถึง 0.16 เมื่อ epoch เพิ่มขึ้น — บานออก = weight กำลังเคลื่อนที่ = กำลังเรียนรู้; ถ้าแถบแบนนิ่งเป็นเส้นตรงแปลว่า weight แทบไม่ถูกอัปเดตเลย ซึ่งเป็นเบาะแสของ vanishing gradient หรือ learning rate ที่เล็กเกินไป. เครื่องมือชิ้นนี้คือสิ่งที่ §7 จะใช้ทั้งหมด.

ต้องรู้ก่อน — เปอร์เซ็นไทล์ อ่านอย่างไร

ถ้าเรียงตัวเลขจากน้อยไปมาก "เปอร์เซ็นไทล์ที่ 50" (median) คือค่าที่อยู่ตรงกลาง — มีครึ่งหนึ่งน้อยกว่ามัน อีกครึ่งมากกว่ามัน. "เปอร์เซ็นไทล์ที่ 84" คือค่าที่มี 84% ของข้อมูลน้อยกว่ามัน.

ลองกับ 5 ตัวเลข: bias ของ layer หนึ่ง = \(-0.2,\ -0.1,\ 0.0,\ 0.1,\ 0.3\). เรียงแล้ว median = 0.0 (ตัวกลาง), minimum = −0.2, maximum = 0.3 ⇒ ความกว้างของแถบ = \(0.3 - (-0.2) = 0.5\). ถ้า epoch ถัดไปกลายเป็น \(-0.5, -0.2, 0.0, 0.25, 0.6\) ⇒ ความกว้าง = 1.1 นั่นคือ "แถบบานออก" ที่เราพูดถึง.

คำนวณ: การเทรนใน Exercise นี้มีกี่ step ต่อ epoch
ให้ X_train shape (1000, 2), validation_split=0.2, ไม่ระบุ batch_size (ค่า default ของ Keras = 32)
  1. ขั้นที่ 1 — แบ่ง validation ออกจาก train
    $$\text{validation} = 0.2 \times 1000 = 200,\qquad \text{train} = 1000 - 200 = 800$$

    จุดที่พลาดกันบ่อย: validation_split ตัดออกจากข้อมูลที่ส่งเข้ามา ⇒ จำนวนที่ใช้เทรนจริงเหลือ 800 ไม่ใช่ 1,000

  2. ขั้นที่ 2 — หาจำนวน batch ต่อ epoch จากส่วนที่เหลือ
    $$\left\lceil \frac{800}{32} \right\rceil = 25$$

25 step ต่อ epoch — ตรงกับ progress bar 25/25 ที่ขึ้นทุก epoch ในสคริปต์ที่รันในคาบ. ตัวเลขนี้ใช้ตรวจความเข้าใจได้ดี: ถ้าเห็น 32/32 แปลว่าลืมหัก validation ออก (1000/32 = 31.25 ⇒ 32).

7. ทดลองดู Vanishing/Exploding Gradient ด้วย TensorBoard

ทำไมหัวข้อนี้มาอยู่ตรงนี้: Lesson 5 พิสูจน์ด้วยสูตรว่า gradient หดหายหรือระเบิดได้เมื่อ network ลึก แต่ตอนนั้นเรายัง "มองไม่เห็น" มัน. ตอนนี้เรามี TensorBoard แล้ว อาจารย์จึงพาย้อนกลับมาทำการทดลองสามชุดบนข้อมูล Circle ชุดเดียวกัน (หน้า 14) เปลี่ยนทีละอย่างแล้วดู histogram ว่าอะไรเกิดขึ้นกับ weight จริงๆ. นี่คือทักษะ "วินิจฉัยโรค" ที่ข้อสอบชอบถามในรูป "เห็นอาการแบบนี้ สาเหตุคืออะไร".

อาจารย์ทำสีคำว่า Gradients vanishing ไว้ แล้วอธิบายต่อว่ามันทำให้ gradient เล็กลงเรื่อยๆ เมื่อไล่ลงไปยัง layer ล่าง ผลคือการอัปเดตแบบ gradient descent ทิ้งให้ weight ของ layer ล่าง virtually unchanged (แทบไม่เปลี่ยน) และ training never converges to a good solution. สองวลีที่ขีดเส้นใต้นี้คือ "อาการ" ที่เราจะไปหาหลักฐานใน TensorBoard.

ทำไมถึงเป็นอย่างนั้น? ตัวการคือบรรทัด kernel_initializer=RandomUniform(0,1). ลองตามตัวเลขดู:

คำนวณประมาณการ: weight เป็นบวกทั้งหมด ทำให้ tanh อิ่มตัวและ gradient หายอย่างไร
ให้ (สมมติเพื่อดูกลไก) แต่ละ layer มี 5 unit, activation จาก layer ก่อนหน้าประมาณ 0.9 ทุกตัว, weight เฉลี่ย 0.5 (ค่ากลางของช่วง 0 ถึง 1), bias 0
  1. ขั้นที่ 1 — หา \(z\) ของ unit หนึ่งตัว
    $$z \approx \sum_{j=1}^{5} \theta_j\, a_j = 5 \times (0.5 \times 0.9) = 2.25$$

    หัวใจอยู่ตรงนี้: เพราะ weight เป็นบวกทั้งหมด พจน์ทั้ง 5 จึงบวกกันเข้าไปเรื่อยๆ ไม่มีตัวลบมาหักล้าง. ถ้า weight มีทั้งบวกและลบคละกัน (เฉลี่ย 0) ผลรวมจะแกว่งอยู่แถว 0 แทน

  2. ขั้นที่ 2 — หา activation
    $$a = \tanh(2.25) = 0.978$$

    เข้าใกล้เพดาน 1 แล้ว และ layer ถัดไปจะได้ input ประมาณ 0.98 ทำให้ \(z\) ยิ่งใหญ่ขึ้นอีก — ปัญหาทบตัวเองไปตามความลึก

  3. ขั้นที่ 3 — หาความชันของ tanh ที่จุดนั้น (จาก Lesson 3: \(g'(z) = 1 - \tanh^2 z\))
    $$g'(2.25) = 1 - 0.978^2 = 1 - 0.9565 = 0.0435$$

    ความชันสูงสุดของ tanh คือ 1 (ที่ \(z=0\)) แต่ตรงนี้เหลือ 0.0435 = ประมาณ 4% ของค่าสูงสุด

  4. ขั้นที่ 4 — ตัวคูณที่ backprop ต้องผ่านต่อ 1 layer
    $$\theta \times g'(z) \approx 0.5 \times 0.0435 = 0.0217$$
  5. ขั้นที่ 5 — คูณข้ามทั้ง 5 layer (chain rule จาก Lesson 5)
    $$0.0217^{5} \approx 4.9 \times 10^{-9}$$

gradient ที่เดินทางถึง layer แรกสุดเหลือขนาดระดับ \(10^{-9}\) เทียบกับตอนออกจาก output. คูณด้วย learning rate 0.01 อีกที การอัปเดตต่อก้าวอยู่ระดับ \(10^{-11}\) — เล็กจน weight "แทบไม่เปลี่ยน" ตรงกับคำที่สไลด์ขีดเส้นใต้ไว้ว่า virtually unchanged. (ตัวเลข 0.9 กับ 0.5 เป็นค่าสมมติเพื่อให้เห็นกลไก ของจริงแต่ละ unit ไม่เท่ากัน แต่ข้อสรุปเชิงขนาด — เล็กลงแบบทวีคูณตามความลึก — ไม่เปลี่ยน.)

ทางแก้ที่ 1 — เปลี่ยนเป็น ReLU + He initialization. สไลด์สั่งสั้นๆ ว่า "Change the code and observe the weight of each layer" โดยเปลี่ยน activation='tanh' เป็น 'relu' และ kernel_initializer=RandomUniform(0,1) เป็น 'he_normal'. เหตุผลของทั้งสองอย่างมาจาก Lesson 5 ตรงๆ: ReLU มีความชัน 1 คงที่เมื่อ \(z > 0\) จึงไม่มีการอิ่มตัวให้ gradient หาย; ส่วน He initialization สุ่ม weight จากการแจกแจงที่มีค่าเฉลี่ย 0 และ variance \(2/n_{in}\) ⇒ ผลรวม \(z\) ไม่พุ่งไปทางบวกอย่างเดียว.

ผลที่เห็นใน histogram ของแผงบน (layer ชื่อ dense_92 ถึง dense_97): แถบของ bias_0 เริ่มจากศูนย์แล้วบานออกเรื่อยๆ ตลอด 20 epoch จนครอบคลุมช่วงราว \(+0.1\) ถึง \(-0.2\) ส่วนแถบ kernel_0 กว้างประมาณ \(\pm0.8\) และค่อยๆ ขยับ — แปลว่า weight ทุก layer กำลังถูกอัปเดตจริง. ในสคริปต์ที่รันในคาบ โมเดลชุดนี้ (ReLU + He, SGD lr = 0.01, momentum 0.9) เทรน 50 epoch แล้วได้ accuracy: 0.7538 - loss: 0.5176 - val_accuracy: 0.7500 - val_loss: 0.5165 — จาก 0.5163 (เดาสุ่ม) ขึ้นมาเป็น 0.75 เพราะแก้แค่สองคำในโค้ด.

คำถามต่อของสไลด์ — "How about slow learning rate?" อาจารย์ทดลองอีกกรณีหนึ่งคือใช้ SGD ที่ learning rate 0.0001 และ momentum 0.9 แล้วดู histogram ของ dense_116/dense_117 ที่มุมขวาล่าง: แกนตั้งของ bias_0 ไล่แค่ \(+2\times10^{-4}\) ถึง \(-4\times10^{-4}\) (เทียบกับแผงบนที่ไล่ถึง \(\pm0.2\) — เล็กกว่าราว 500–1,000 เท่า) และแถบ kernel_0 เป็นแนวราบแทบไม่ขยับเลยตลอด 20 epoch.

ตรงนี้คือบทเรียนที่ลึกที่สุดของหน้านี้: กราฟ "แบนราบ" เหมือนกัน แต่สาเหตุคนละเรื่อง — กรณีหน้า 15 weight ไม่ขยับเพราะ \(\nabla J \approx 0\) (gradient หาย), กรณีนี้ weight ไม่ขยับเพราะ \(\alpha\) เล็กมาก ทั้งที่ gradient ปกติดี. ดูจากสูตรเดียวกัน \(\Delta\theta = -\alpha\,\nabla J\) จะเห็นว่าผลคูณเล็กได้จากสองทาง. วิธีแยกในทางปฏิบัติ: ถ้าลองเพิ่ม learning rate แล้วแถบเริ่มบานออก แปลว่าเป็นโรคที่สอง; ถ้าเพิ่มแล้วยังนิ่ง (หรือ layer บนขยับแต่ layer ล่างนิ่ง) แปลว่าเป็นโรคแรก.

โค้ดทำอะไร
Dense(5, kernel_initializer='he_normal') ไม่มี activationจงใจไม่ใส่ activation= เพื่อให้ layer คืนค่า \(z\) ดิบๆ ออกมาก่อน
BatchNormalization()ทำให้ \(z\) ของแต่ละ mini-batch มีค่าเฉลี่ย 0 และความแปรปรวน 1 (แล้วปรับด้วยพารามิเตอร์ \(\gamma, \beta\) ที่เรียนรู้ได้) — Lesson 5 §Batch Norm
Activation('relu')ค่อยผ่าน activation หลังจาก normalize แล้ว ⇒ input ของ ReLU อยู่ในช่วงที่ควบคุมได้เสมอ
ลำดับ Dense → BN → Activationคือความหมายของคอมเมนต์ # normalize before. อีกแบบคือ Dense(relu) → BN ("normalize after") ซึ่งสคริปต์ในคาบเอามาเทียบกัน — ทั้งสองแบบใช้ได้ ตำราถกเถียงกันว่าแบบไหนดีกว่า
Dense(1) → BatchNormalization() → Activation('sigmoid')ใส่ BN ก่อน sigmoid ของ output ด้วย (ปกติไม่ค่อยทำกัน แต่สไลด์ทำเพื่อความสม่ำเสมอ)
SGD(learning_rate=0.10, momentum=0.9)เหมือนหน้า 17 เป๊ะ — ประเด็นทั้งหมดคือ BN ทำให้ learning rate ที่เคยพังกลับใช้ได้

ผลลัพธ์ที่คาด: กราฟในสไลด์แสดง epoch_accuracy ไต่ขึ้นจากราว 0.47 ไปถึงประมาณ 0.80 และ epoch_loss ลดจากราว 0.72 ลงมาราว 0.45 ตลอดแกน 0–100 และ kernel/histogram มีแถบที่บานออกจาก \(\pm0.4\) เป็นราว \(-0.8\) ถึง \(+1.2\) — ทั้งสามอย่างคือสัญญาณว่าเรียนรู้ได้จริง. ในสคริปต์ที่รันในคาบ รุ่น "normalize after" ที่ learning rate 0.2 ให้ accuracy: 0.7937 - loss: 0.4558 ที่ epoch 50 เทียบกับ 0.5088 / 0.6943 ของรุ่นไม่มี BN ที่ learning rate เดียวกัน.

คำนวณ: Batch Normalization "ดึงกลับ" ค่าที่ใหญ่เกินอย่างไร
ให้ \(z\) ของ 1 neuron ใน mini-batch 4 ตัวอย่าง = 2, 4, 6, 8 ; \(\gamma = 1,\ \beta = 0\) (ละ \(\epsilon\) ที่เล็กมาก)
  1. ขั้นที่ 1 — ค่าเฉลี่ยของ batch
    $$\mu = \frac{2+4+6+8}{4} = \frac{20}{4} = 5$$
  2. ขั้นที่ 2 — ความแปรปรวนของ batch
    $$\sigma^2 = \frac{(2-5)^2 + (4-5)^2 + (6-5)^2 + (8-5)^2}{4} = \frac{9+1+1+9}{4} = 5$$

    ความแปรปรวนคือ "ค่าเฉลี่ยของระยะห่างกำลังสองจากค่าเฉลี่ย" — ยิ่งมากแปลว่าข้อมูลยิ่งกระจาย

  3. ขั้นที่ 3 — normalize ด้วย \(\hat z = (z-\mu)/\sqrt{\sigma^2}\)
    $$\hat z = \frac{-3}{\sqrt5},\ \frac{-1}{\sqrt5},\ \frac{1}{\sqrt5},\ \frac{3}{\sqrt5} = -1.342,\ -0.447,\ 0.447,\ 1.342$$
  4. ขั้นที่ 4 — ลองเปลี่ยน \(z\) ให้ใหญ่ขึ้น 100 เท่า (200, 400, 600, 800) แล้วทำซ้ำ
    $$\mu = 500,\quad \sigma^2 = 50000,\quad \hat z = \frac{-300}{\sqrt{50000}} = -1.342,\ \ldots$$

    ได้ชุดเดิมเป๊ะ เพราะทั้งตัวเศษและตัวส่วนโตขึ้นเป็นสัดส่วนเดียวกัน

ไม่ว่า \(z\) ที่ไหลเข้ามาจะใหญ่แค่ไหน ค่าที่ส่งต่อไปยัง activation ถัดไปจะอยู่ราว \(\pm1.3\) เสมอ ⇒ (ก) ไม่ระเบิด และ (ข) ไม่ตกไปอยู่ในโซนอิ่มตัวของ tanh/sigmoid. นี่คือเหตุผลที่ BN แก้ได้ทั้งสองโรคด้วยกลไกเดียว และเป็นเหตุผลที่หน้า 18 ใช้ learning rate 0.10 ตัวเดิมที่หน้า 17 พังได้อย่างปลอดภัย.

โมเดล tanh 5 ชั้นที่ใช้ RandomUniform(0,1) เทรนไม่ขึ้น (accuracy ค้างที่ 0.5163) เพราะเหตุผลเชิงกลไกใดมากที่สุด?
คำถาม 10วินิจฉัยจาก histogram
histogram ของ TensorBoard แสดงแถบ kernel_0 ที่แบนราบตลอด 20 epoch และแกนของ bias_0 ไล่แค่ระดับ 1e-4 โมเดลใช้ ReLU กับ he_normal อยู่แล้ว สาเหตุที่น่าจะเป็นมากที่สุดคือ?
ออกสอบสูง — ข้อความที่อาจารย์ทำสี
  • Gradients vanishing — gradient เล็กลงเรื่อยๆ เมื่อไล่ลงไป layer ล่าง ผลคือ weight ของ layer ล่าง "virtually unchanged" และ "training never converges to a good solution". กับดัก: ตัวเลือกที่บอกว่า layer บน ต่างหากที่ไม่อัปเดต
  • Exploding gradients — ตรงข้ามกัน: ค่าใหญ่เกินจนไม่เสถียร. กับดัก: สลับนิยามกับ vanishing
  • unstable network — คำนี้คือคำตอบของ "exploding gradient ทำให้เกิดอะไร": at best เรียนรู้ไม่ได้, at worst weight เป็น NaN ที่อัปเดตต่อไม่ได้. กับดัก: ตัวเลือกที่บอกว่า exploding ทำให้โมเดล overfit
  • สามอาการของ exploding ที่ต้องจำเรียงกัน: (1) โมเดลจับข้อมูล train ไม่ได้ (loss แย่), (2) ไม่เสถียร loss เปลี่ยนแรงระหว่าง update, (3) loss กลายเป็น NaN
  • จุดที่ข้อสอบเติมโค้ดมักถาม: คู่ activation='relu' ↔ kernel_initializer='he_normal' (ReLU คู่ He, sigmoid/tanh คู่ Xavier/Glorot — หน้า 22); ลำดับ Dense → BatchNormalization() → Activation('relu') สำหรับ "normalize before"; และตัวแปรเดียวที่ต่างระหว่างหน้า 17 กับหน้า 18 คือการแทรก BN (learning rate 0.10 เท่ากัน)

8. Hyperparameter Tuning: มีอะไรให้ปรับ และค่าเริ่มต้นที่ควรใช้

ปัญหาก่อน: ตลอดห้าบทที่ผ่านมา ทุกครั้งที่เขียนโค้ดเราต้อง "เลือกตัวเลข" เต็มไปหมด — Dense(10) ทำไมไม่ใช่ 20? learning_rate=0.03 ทำไมไม่ใช่ 0.003? กี่ layer ดี? dropout เท่าไร? ที่ผ่านมาเราเลือกตามที่อาจารย์บอกหรือตามความรู้สึก. หน้า 19–32 ตอบคำถามว่าจะเลือกอย่างมีระบบได้อย่างไร.

อาจารย์เปิดด้วยการเปรียบเทียบที่จำง่าย: hyperparameter เหมือนปุ่มหมุนบนวิทยุเก่า ที่ต้องค่อยๆ หมุนหาจนเสียงชัดที่สุด (คำบรรยายใต้ภาพเขียนว่า "Hyperparameters are like knobs that we need to tune to yield the best performance"). สามประโยคที่ทำสีไว้เรียงกันเป็นเหตุผลครบชุด:

  • Hyperparameter tuning finds the best hyperparameter combination for minimizing cost functions — นิยาม. คำสำคัญคือ combination: เราไม่ได้หาค่าที่ดีที่สุดของแต่ละปุ่มแยกกัน แต่หาชุดที่ดีที่สุดพร้อมกัน เพราะปุ่มส่งผลกระทบต่อกัน (เช่น batch size ใหญ่มักต้องการ learning rate ใหญ่ตาม)
  • Hyperparameters can be tuned in a manual or automatic way — มีสองทางเลือก: หมุนเอง หรือให้โปรแกรมหมุน
  • In deep neural networks, manually tuning hyperparameters can be suboptimal and time-consuming — และเพราะเหตุนี้ Automatic hyperparameter tuning จึงเป็น more efficient approach. สองคำที่ทำสีต้องแยกให้ออก: suboptimal = ได้คำตอบที่ไม่ดีที่สุด (คุณภาพ), time-consuming = เปลืองเวลา (ต้นทุน) — คนละปัญหากัน และการจูนอัตโนมัติแก้ได้ทั้งคู่

ทำไม "โมเดลลึก" ถึงทำให้การจูนด้วยมือแย่เป็นพิเศษ? เพราะจำนวนปุ่มโตตามความลึก (ทุก layer เพิ่มมาก็มีจำนวน unit, activation, dropout rate ของตัวเอง) และการเทรนแต่ละครั้งใช้เวลานาน. คนที่หมุนปุ่มเองจึงลองได้ไม่กี่ชุดและมักติดอยู่กับ "ชุดที่คุ้นเคย" แทนที่จะสำรวจให้ทั่ว.

สไลด์บอกว่า Hyperparameters can be categorized into three main categories ซึ่งเป็นโครงที่ควรท่องให้ได้ เพราะข้อสอบชอบถามว่า "ข้อใดอยู่ในหมวดใด". วิธีจำที่ได้ผลคือถามว่าแต่ละหมวดตอบคำถามอะไร:

หมวด (ชื่อตามสไลด์)ตอบคำถามว่าสมาชิกครบตามสไลด์
Network architectureโมเดล "ใหญ่/รูปร่างอย่างไร"จำนวน hidden layer (network depth), จำนวน neuron ในแต่ละ layer (layer width), activation type
Learning and optimizationโมเดล "เรียนรู้อย่างไร" (ไปถึง error ต่ำสุดด้วยวิธีใด)learning rate และ decay schedule, batch size, optimization algorithms, weight initialization, batch normalization (ช่วยลด overfitting ด้วย), จำนวน iteration/epoch
Strategies to avoid overfittingกัน "ท่องจำข้อสอบเก่า" อย่างไรL2 regularization, dropout layers, data augmentation

สังเกตรายละเอียดที่สไลด์วงเล็บไว้: Batch Normalization (also mitigate overfitting) — BN ถูกจัดอยู่หมวดที่ 2 แต่มีผลข้างเคียงช่วยหมวดที่ 3 ด้วย เพราะสถิติของ mini-batch ที่ต่างกันทุกก้าวทำหน้าที่เป็น noise เล็กๆ คล้าย regularization. ข้อสอบชอบใช้ตัวนี้เป็นตัวหลอกเพราะตอบได้สองหมวด — ถ้าถามว่า "จัดอยู่หมวดไหน" ให้ตอบตามที่สไลด์จัดคือ Learning and optimization.

หน้า 21 เจาะหมวดแรก. หัวข้อย่อยแรกคือ Number of hidden layers and number of neurons และคำแนะนำของอาจารย์สวนสัญชาตญาณของมือใหม่: ให้เลือกโมเดลที่มี layer และ neuron มากกว่าที่จำเป็นจริงๆ เพื่อให้ความจุ (capacity) "large enough" พอจะเรียนรู้ลักษณะของข้อมูลได้ — แต่วงเล็บไว้ว่า but not too complexity. แล้วประโยคที่ทำตัวหนาคือกลยุทธ์: Key is to observe the performance and then fine-tune as needed — คือเริ่มใหญ่ไว้ก่อน ดูผล แล้วค่อยหด. เหตุผลที่ต้องหดก็เพราะถ้าให้ความจุมากเกินไป โมเดล "may tend to overfit the data and memorize the training set" และเมื่อเจออาการนั้นให้ลดจำนวน hidden unit ลงหรือใช้วิธีของหมวดที่ 3.

หัวข้อย่อยที่สองคือ Activation type ซึ่งอาจารย์ให้คำตอบสำเร็จรูปเลย: ReLU และตระกูลของมันเป็น default ที่ดีสำหรับทุก hidden layer; ส่วน output layer "really depends on your task" (งานสองคลาสใช้ sigmoid, หลายคลาสใช้ softmax, ทำนายตัวเลขใช้ linear — ตาม Lesson 3). นี่คือ hyperparameter ที่ไม่ต้องเสียเวลาค้นหา เพราะมีกฎชัดเจนอยู่แล้ว.

Number of training iterations or epochsไม่จำเป็นต้องจูนเลย — ตั้งจำนวน epoch ไว้เยอะๆ แล้วใช้ early stopping แทน§2 ของบทนี้

สองบรรทัดสุดท้ายคือของแถมที่มีค่าที่สุดสำหรับข้อสอบ: การเลือก initializer ไม่ใช่การค้นหา แต่เป็นการจับคู่กับ activation (ReLU↔He, sigmoid/tanh↔Xavier) และ จำนวน epoch ไม่ใช่ hyperparameter ที่ต้องค้นหา เพราะ EarlyStopping จัดการให้แล้ว. สองข้อนี้ตัดมิติของพื้นที่ค้นหาออกไปได้ฟรีๆ ซึ่งสำคัญมากเมื่อเห็นตัวเลขใน §9.

หน้า 23 ไล่หมวดที่สาม และรูปแบบของทุกบรรทัดเหมือนกันหมดคือ "เครื่องมือ → ปุ่มที่ต้องจูนของมัน" ซึ่งเป็นสิ่งที่ต้องจำเป็นคู่:

  • L2 regularization → จูน regularization parameter (lambda) คือ \(\lambda\) ในพจน์โทษ \(\frac{\lambda}{2m}\sum\theta^2\) ของ Lesson 4. \(\lambda\) ใหญ่ = บีบ weight ให้เล็ก = โมเดลเรียบขึ้น (underfit ได้ถ้ามากไป)
  • Dropout layers → จูน dropout rate = สัดส่วนของ unit ที่ถูกปิดสุ่มในแต่ละก้าว (เช่น 0.2 = ปิด 20%). สูงไปโมเดลเรียนไม่ทัน ต่ำไปก็ไม่ช่วย
  • Batch normalization → จูน mini-batch size หรือ momentum parameter ถ้าจำเป็น (ตัวเดียวกับที่หน้า 22 บอกค่า 0.9/0.99/0.999)
  • Data augmentation → จูน random transformations metrics คือพารามิเตอร์ของการแปลงข้อมูลแบบสุ่ม (หมุนกี่องศา ซูมเท่าไร พลิกซ้ายขวาไหม) — เป็นการ "สร้างข้อมูลใหม่จากของเดิม" จึงลด overfitting ที่ต้นเหตุคือข้อมูลน้อย

สังเกตว่า Batch normalization โผล่มาทั้งหน้า 20, 22 และ 23 — ย้ำอีกครั้งว่ามันมีสองบทบาท.

  2. สร้างโมเดลที่รับค่าเหล่านั้น — Build the corresponding model. คำว่า corresponding คือโมเดลที่ "สอดคล้อง" กับ search space นั้น ๆ คือเขียนให้ตัวเลขที่จะจูนกลายเป็นตัวแปรแทนที่จะเป็นค่าตายตัว
  3. เลือกอัลกอริทึมค้นหา — Define the search algorithm ซึ่งมีหน้าที่เลือก next set of hyperparameters ที่จะลองต่อไป โดยอัตโนมัติ ตาม selected search algorithm. นี่คือหัวใจ: สิ่งที่ทำให้ Grid / Random / HyperBand / Bayesian ต่างกันคือวิธีเลือกชุดถัดไป ไม่ใช่วิธีเทรน
  4. เซฟตัวที่ดีที่สุดแล้ววัดผลบน test set — Save the best model and measure performance on your test set. ย้ำว่า test set ใช้ตอนท้ายเท่านั้น ไม่เอามาร่วมตัดสินใจระหว่างค้นหา

  • Hyperparameters แบ่งเป็น three main categories — ต้องจำชื่อสามหมวดและสมาชิกให้ได้ โดยเฉพาะว่า Batch Normalization อยู่หมวด Learning and optimization (แต่ช่วยลด overfitting ด้วย) และ จำนวน epoch อยู่หมวดนั้นเช่นกัน
  • Number of hidden layers and number of neurons — เริ่มใหญ่พอ (large enough) แล้วสังเกตผลและ fine-tune; ถ้าความจุเกินจะ memorize training set. กับดัก: "เริ่มเล็กที่สุดแล้วค่อยเพิ่ม"
  • Activation type — ReLU และตระกูลเป็น default ของ hidden layer ทุกชั้น ส่วน output ขึ้นกับงาน
  • Weight Initialization — He สำหรับ ReLU, Xavier (Glorat) สำหรับ sigmoid/tanh เป็นข้อที่ออกสอบบ่อยที่สุดของหน้านี้ กับดักคือสลับคู่กัน
  • Number of training iterations or epochs — ไม่ต้องจูน ใช้ epoch เยอะๆ + early stopping. กับดัก: "ต้องหา epoch ที่ดีที่สุดด้วย grid search"

9. อัลกอริทึมค้นหา: Grid, Random, HyperBand, Bayesian

ปัญหาก่อน: ขั้นที่ 3 ของหน้า 24 บอกให้ "เลือก search algorithm" — แต่เลือกจากอะไร? ทั้งสี่ตัวทำงานเดียวกันคือ "เลือกชุด hyperparameter ชุดถัดไปที่จะลอง" ต่างกันแค่วิธีเลือก และความต่างนั้นแปลเป็นเวลาที่ต่างกันเป็นร้อยเท่า. ไล่จากโง่ที่สุดไปฉลาดที่สุด.

Grid Search คือวิธีที่ตรงไปตรงมาที่สุด: สไลด์บอกว่ามัน explores predefined combinations ของค่า hyperparameter ด้วย systematic brute-force search — แต่ละ hyperparameter ได้รับ "เซ็ตของค่าผู้สมัคร" มาชุดหนึ่ง แล้วโมเดลถูกเทรนและประเมินทุกการจับคู่ที่เป็นไปได้ (every combination). สไลด์ระบุเงื่อนไขการใช้ไว้ชัด: ได้ผลดีเมื่อ model is relatively simple และ search space is small; ส่วนกับ Deep Learning มันเป็นวิธีที่ computationally expensive เพราะต้องเทรนซ้ำหลายชุดมาก.

อ่านรูป Grid Layout ให้ได้ประเด็น: แกนนอนของรูปคือพารามิเตอร์ที่ "สำคัญ" (important parameter — เส้นโค้งสีเขียวด้านบนแสดงว่าคะแนนเปลี่ยนแปลงมากตามแกนนี้ และมียอดแหลมอยู่จุดหนึ่ง) ส่วนแกนตั้งคือพารามิเตอร์ที่ "ไม่สำคัญ" (unimportant parameter — เส้นสีเหลืองด้านซ้ายแทบแบน คะแนนแทบไม่เปลี่ยนไม่ว่าจะตั้งค่าใด). การทดลองทั้งหมดมี 9 จุด = 3 ค่าของแกนนอน × 3 ค่าของแกนตั้ง. ผลคือเราจ่ายค่าเทรน 9 ครั้ง แต่ได้ข้อมูลเกี่ยวกับพารามิเตอร์สำคัญแค่ 3 ค่าเท่านั้น — อีก 6 ครั้งคือการลองค่าเดิมซ้ำโดยเปลี่ยนปุ่มที่ไม่มีผล. และถ้ายอดของเส้นเขียวบังเอิญอยู่ระหว่างสองค่าที่เราเลือก เราจะพลาดมันไปเลย ซึ่งคือสิ่งที่สไลด์ทำสีแดงไว้ว่าได้ (suboptimal solution) — Grid Search หา "ค่าที่ดีที่สุดภายในตารางที่กำหนดไว้ล่วงหน้า" ได้จริง แต่ไม่รับประกันว่าดีที่สุดจริงๆ เพราะอาจพลาดค่าที่อยู่ระหว่างหรือนอกตาราง.

คำนวณ: Grid Search ต้องเทรนกี่ครั้งสำหรับ search space ของสไลด์หน้า 29
ให้ พื้นที่ค้นหาจากโค้ดหน้า 29: num_layers ∈ {1, 2}; units_i ∈ [10, 50] step 1 = 41 ค่าต่อ layer; activation ∈ {relu, elu, selu} = 3 ค่า (ใช้ร่วมกันทุก layer); dropout_i ∈ {0, 0.1, …, 0.5} = 6 ค่าต่อ layer; lr เป็นค่าต่อเนื่อง — สมมติว่าเราทำเป็นตาราง 5 ค่า
  1. ขั้นที่ 1 — กรณี 1 layer (มี units และ dropout อย่างละชุดเดียว)
    $$41 \times 3 \times 6 = 738$$
  2. ขั้นที่ 2 — กรณี 2 layer (units และ dropout มีอย่างละ 2 ชุด จึงยกกำลังสอง)
    $$41^2 \times 3 \times 6^2 = 1681 \times 3 \times 36 = 181{,}548$$
  3. ขั้นที่ 3 — รวมสองกรณี แล้วคูณด้วยจำนวนค่าของ learning rate
    $$(738 + 181{,}548) \times 5 = 182{,}286 \times 5 = 911{,}430$$

ประมาณ 911,430 ครั้งของการเทรน. ถ้าครั้งละ 1 นาทีก็ใช้เวลาราว 1.7 ปี. เทียบกับสไลด์หน้า 31 ที่ค้นด้วย Hyperband ใช้เพียง 211 trial และเวลา 43 นาที 46 วินาที. นี่คือความหมายรูปธรรมของคำว่า computationally expensive: จำนวนชุดโตแบบคูณตามจำนวนตัวเลือกของทุกปุ่ม (เพิ่มปุ่มใหม่ที่มี 10 ค่า = งานเพิ่ม 10 เท่าทันที).

Random Search แก้ปัญหาข้างบนด้วยไอเดียที่ดูไม่น่าจะได้ผลแต่ได้ผลจริง: แทนที่จะลองทุกการจับคู่ ให้สุ่มชุดค่าขึ้นมาตามจำนวนครั้งที่เรากำหนดเอง (a specified number of randomly selected hyperparameter combinations) โดยแต่ละ trial สุ่มค่าของแต่ละ hyperparameter จากช่วงหรือรายการที่นิยามไว้.

อ่านรูป Random Layout เทียบกับรูปก่อนหน้า: จำนวนจุดเท่ากันคือ 9 จุด (งบเท่ากัน) แต่คราวนี้ไม่มีจุดไหนมีพิกัดแกนนอนซ้ำกันเลย ⇒ พารามิเตอร์สำคัญถูกทดสอบถึง 9 ค่าที่ต่างกัน เทียบกับ 3 ค่าของ Grid. โอกาสที่จะมีจุดใดจุดหนึ่งตกใกล้ยอดของเส้นโค้งสีเขียวจึงสูงกว่ามาก ทั้งที่จ่ายเท่ากัน. นี่คือความหมายของวลีที่สไลด์เน้นว่า fewer, more diverse combinations และเหตุผลที่มัน more efficient than Grid Search โดยเฉพาะเมื่อ "only some hyperparameters have a strong effect on model performance" — ซึ่งเป็นสถานการณ์ปกติของ deep learning.

แต่สไลด์ก็ทำสีแดงจุดอ่อนไว้ด้วย: Random Search เป็น blind search — มัน does not use results from previous trials ในการตัดสินใจว่าจะลองอะไรต่อ. trial ที่ 30 สุ่มแบบเดียวกับ trial ที่ 1 เป๊ะ ทั้งที่ตอนนั้นเรามีข้อมูลแล้ว 29 จุดว่าย่านไหนดีย่านไหนแย่. ผลคือ "it may miss promising regions or the best hyperparameter combination within the search space" — มันอาจเดินผ่านย่านที่มีแวว แล้วไม่กลับไปขุดต่อ. สองอัลกอริทึมที่เหลือคือการแก้ข้อนี้คนละทาง.

HyperBand โจมตีจากอีกมุม: แทนที่จะฉลาดขึ้นเรื่อง "เลือกอะไรต่อ" มันฉลาดเรื่อง "จ่ายเท่าไรให้แต่ละตัว". สไลด์บอกว่า HyperBand ใช้วิธี successive halving ในแต่ละรอบด้วย different budgets เพื่อหา best configurations และขยายความว่า: มันใช้ successive halving เพื่อระบุและให้ความสำคัญกับ configuration ที่มีแววอย่างรวดเร็ว พร้อมทั้งทิ้งตัวที่ดูไม่มีแวว; configuration ที่รอดจากการคัดออกจะได้รับงบเพิ่ม (The configurations that survive the elimination are given additional budgets) ทำซ้ำจนเหลือเพียงไม่กี่ตัว และจบเมื่อใช้งบสูงสุดครบ.

สัญชาตญาณเบื้องหลังคือข้อสังเกตง่ายๆ: configuration ที่แย่มักแย่ตั้งแต่ epoch แรกๆ เราไม่จำเป็นต้องเทรนมันครบ 81 epoch ถึงจะรู้. กราฟด้านซ้ายของสไลด์แสดงเส้น loss ของหลาย configuration ที่งบน้อย — เห็นชัดว่าบางเส้นดิ่งลงเร็ว บางเส้นแทบไม่ขยับ ⇒ ตัดเส้นที่ไม่ขยับทิ้งได้ตั้งแต่ยังจ่ายไปนิดเดียว.

ตารางด้านขวาคือการจัดสรรงบจริง โดยมีหัวตารางกำกับว่า max_iter = 81, eta = 3, \(B = 5 \times \text{max\_iter}\). สูตรของแต่ละ bracket คือ (ให้ \(n\) = จำนวน configuration เริ่มต้น, \(r\) = งบเริ่มต้นต่อตัว, \(\eta\) = ตัวหารการคัดออก):

$$n_i = \left\lfloor n\,\eta^{-i} \right\rfloor,\qquad r_i = r\,\eta^{\,i}$$

ทุกรอบถัดไป จำนวนผู้รอดหารด้วย \(\eta\) ส่วนงบต่อตัวคูณด้วย \(\eta\)

คำนวณ: bracket \(s=4\) ของตารางในสไลด์ (max_iter = 81, \(\eta = 3\), \(n = 81\), \(r = 1\))
ให้ คอลัมน์ \(s=4\) ของตาราง ซึ่งมีแถว \(i = 0\) ถึง \(4\)
  1. ขั้นที่ 1 — หา \((n_i, r_i)\) ทีละรอบ
    $$\begin{aligned} i=0:&\; n_0 = \lfloor 81 \cdot 3^{0} \rfloor = 81,\;\; r_0 = 1 \cdot 3^0 = 1\\ i=1:&\; n_1 = \lfloor 81/3 \rfloor = 27,\;\; r_1 = 1\cdot3 = 3\\ i=2:&\; n_2 = \lfloor 81/9 \rfloor = 9,\;\; r_2 = 1\cdot9 = 9\\ i=3:&\; n_3 = \lfloor 81/27 \rfloor = 3,\;\; r_3 = 27\\ i=4:&\; n_4 = \lfloor 81/81 \rfloor = 1,\;\; r_4 = 81 \end{aligned}$$

    ตรงกับคอลัมน์ \(s=4\) ของตารางในสไลด์ทุกช่อง (81/1, 27/3, 9/9, 3/27, 1/81)

  2. ขั้นที่ 2 — คิดต้นทุนของแต่ละรอบ = \(n_i \times r_i\)
    $$81\times1 = 81,\quad 27\times3 = 81,\quad 9\times9 = 81,\quad 3\times27 = 81,\quad 1\times81 = 81$$

    ทุกรอบใช้งบเท่ากันพอดี — นี่คือการออกแบบของ successive halving: "ได้งบเพิ่มเป็น \(\eta\) เท่า แต่คนรับลดลง \(\eta\) เท่า" จึงหักล้างกันพอดี

  3. ขั้นที่ 3 — รวมงบทั้ง bracket
    $$5 \times 81 = 405 \text{ epoch}$$
  4. ขั้นที่ 4 — เทียบกับการเทรนทุก configuration ให้เต็มงบ
    $$81 \times 81 = 6{,}561 \text{ epoch}, \qquad \frac{6561}{405} \approx 16.2$$

สำรวจ 81 configuration ด้วยงบ 405 epoch แทนที่จะเป็น 6,561 — ถูกกว่าราว 16 เท่า เพราะตัวที่แย่ถูกตัดทิ้งตั้งแต่ใช้งบไปแค่ 1–3 epoch. คอลัมน์อื่นของตารางคือ bracket ที่เริ่มต้นต่างกัน เช่น \(s=3\) เริ่มที่ (27, 3), \(s=2\) เริ่มที่ (9, 9), \(s=1\) เริ่มที่ (6, 27) และ \(s=0\) คือ (5, 81) ซึ่งไม่ตัดใครเลยแต่ให้งบเต็มทุกตัวตั้งแต่แรก — การมีหลาย bracket ก็เพื่อกันกรณีที่ "ตัวที่ออกตัวช้าแต่ชนะตอนท้าย" ถูกตัดทิ้งไปตั้งแต่แรก. ใน KerasTuner (หน้า 30) พารามิเตอร์ max_epochs=81 และ factor=3 ก็คือ \(\text{max\_iter}=81\) กับ \(\eta=3\) ตัวเดียวกันนี้.

Bayesian Optimization คือตัวที่ "ฉลาดที่สุด" ในสี่ตัว เพราะมันแก้จุดอ่อน blind search ของ Random ตรงๆ. สไลด์บอกว่ามันก็รันโมเดลหลายครั้งด้วยชุดค่าต่างๆ เหมือนกัน แต่มันประเมิน past model information เพื่อ select hyperparameter values สำหรับสร้างโมเดลตัวถัดไป. ผลคือ "requires less iterations to get to the optimal set" เพราะมันตัดย่านที่เชื่อว่าไม่มีอะไรดีทิ้งไป. และสไลด์ระบุ two key components ไว้สองตัวที่ต้องจำคู่กัน:

  • Surrogate model — a probabilistic model that try to learn the true objective function, which forms a mapping ของ hyperparameter ไปยัง "probability score ว่า objective function จะทำได้ดีแค่ไหน". พูดง่ายๆ คือโมเดลตัวแทนที่ราคาถูก: แทนที่จะเทรน network จริง (แพง) เพื่อรู้คะแนนของจุด \(x\) เราให้ surrogate ทำนายให้ (ฟรี) จากจุดที่เคยลองมาแล้ว. ในรูปคือเส้นสีแดงที่พยายามลากตามเส้นประ (true function) โดยอาศัยจุดสีแดงที่สังเกตได้
  • Acquisition Function — utilizes the surrogate model แล้วตัดสินว่าย่านไหน worth exploiting (optimum area = ย่านที่คาดว่าคะแนนดี) และย่านไหน worth exploring (area we haven't yet looked = ย่านที่ยังไม่เคยลอง). พูดง่ายๆ คือตัวตัดสินว่าจะลองจุดไหนต่อ ในรูปคือเส้นสีน้ำเงิน — จุดที่เส้นน้ำเงินสูงสุดคือจุดที่จะถูกเลือกลองต่อไป

แถบสีเขียวในรูปคือช่วงความเชื่อมั่น (Upper/Lower Confidence Interval) ซึ่งกว้างตรงที่ยังไม่มีจุดข้อมูลและแคบตรงที่มีจุดหนาแน่น — นั่นคือ "ความไม่แน่ใจ" \(\sigma(x)\) ที่ acquisition function เอาไปใช้.

ต้องรู้ก่อน — ค่าเฉลี่ยกับความไม่แน่ใจ และ trade-off ระหว่าง "ขุด" กับ "สำรวจ"

เวลาเราทำนายอะไรสักอย่าง มีตัวเลขสองตัวที่ต้องแยกกัน: \(\mu\) (mu) = ค่าที่คาดว่าจะได้, และ \(\sigma\) (sigma) = ความไม่แน่ใจของการคาดนั้น.

ตัวอย่างในชีวิตจริง: ร้านอาหาร A คุณเคยกินมา 20 ครั้ง ชอบทุกครั้ง ⇒ \(\mu\) สูง (8.5/10), \(\sigma\) ต่ำ (0.2) เพราะรู้ดีแล้ว. ร้าน B เพิ่งเปิด ยังไม่เคยกิน เพื่อนบอกว่า "น่าจะโอเค" ⇒ \(\mu\) ต่ำกว่านิดหน่อย (8.0) แต่ \(\sigma\) สูงมาก (2.0) เพราะอาจจะห่วยมากหรืออาจจะเป็นร้านที่ดีที่สุดในชีวิตก็ได้.

ถ้าเหลือมื้อเดียวในชีวิต ควรไป A (ปลอดภัย = exploit); แต่ถ้ายังมีอีกหลายร้อยมื้อ การลอง B คุ้มกว่าเพราะถ้ามันดีจริงเราจะได้กลับไปอีกหลายครั้ง (explore). ตัวเลข \(\lambda\) ในสูตรหน้าถัดไปคือ "ปุ่มปรับความกล้าเสี่ยง" ที่ตัดสินว่าจะเอนไปทางไหน.

สไลด์ใช้ acquisition function แบบ UCB (Upper Confidence Bound) ซึ่งเขียนกำกับไว้บนกราฟทั้งสามรูป:

$$\text{UCB}_\lambda(x) = \mu(x) + \lambda\,\sigma(x)$$

คะแนนที่คาดไว้ บวกโบนัสตามความไม่แน่ใจ โดย \(\lambda\) คือตัวคูณของโบนัส

หมายเหตุใต้รูปของสไลด์สรุปไว้ว่า \(\lambda\) ควบคุม exploration–exploitation trade-off: \(\lambda\) ใหญ่เอื้อย่านที่ไม่แน่ใจ (exploration) ส่วน \(\lambda\) เล็กเอื้อย่านที่คาดว่าคะแนนสูง (exploitation). สังเกตกราฟทั้งสามรูปในสไลด์: ที่ \(\lambda = 0.2\) เส้นน้ำเงินแทบทับเส้นแดง (เชื่อ \(\mu\) เป็นหลัก); ที่ \(\lambda = 1.2\) เริ่มแยกตัวขึ้นตรงย่านที่แถบเขียวกว้าง; ที่ \(\lambda = 5\) เส้นน้ำเงินพุ่งสูงจนสเกลแกนตั้งต้องขยายไปถึง 60 และยอดของมันอยู่ในย่านที่ไม่มีจุดข้อมูลเลย — แปลว่ามันจะไปลองตรงที่ไม่รู้จักก่อน.

คำนวณ: \(\lambda\) ตัดสินใจว่าจะ "ขุดจุดเดิม" หรือ "สำรวจจุดใหม่" อย่างไร
ให้ candidate สองจุด — A (เคยลองใกล้ๆ แล้ว): \(\mu = 0.85,\ \sigma = 0.02\) และ B (ยังไม่เคยลองแถวนี้): \(\mu = 0.80,\ \sigma = 0.20\)
  1. ขั้นที่ 1 — \(\lambda = 0.2\) (เน้น exploit ตามรูปซ้ายของสไลด์)
    $$\text{UCB}(A) = 0.85 + 0.2(0.02) = 0.854$$ $$\text{UCB}(B) = 0.80 + 0.2(0.20) = 0.840$$

    A ชนะ ⇒ ไปขุดต่อในย่านที่รู้ว่าดีอยู่แล้ว

  2. ขั้นที่ 2 — \(\lambda = 1.2\) (รูปกลางของสไลด์)
    $$\text{UCB}(A) = 0.85 + 1.2(0.02) = 0.874$$ $$\text{UCB}(B) = 0.80 + 1.2(0.20) = 1.040$$

    B ชนะขาด เพราะโบนัสความไม่แน่ใจของมัน (0.24) ใหญ่กว่าส่วนต่างของ \(\mu\) (0.05) มาก

  3. ขั้นที่ 3 — \(\lambda = 5\) (รูปขวาของสไลด์)
    $$\text{UCB}(A) = 0.85 + 5(0.02) = 0.95, \qquad \text{UCB}(B) = 0.80 + 5(0.20) = 1.80$$

    ยิ่งห่างกันมากขึ้นไปอีก — แทบไม่สนใจ \(\mu\) แล้ว

จุดที่ค่าเฉลี่ยต่ำกว่า (B: 0.80) ถูกเลือกได้ ถ้า \(\lambda\) ใหญ่พอให้โบนัสความไม่แน่ใจชนะ. จุดพลิกอยู่ที่ \(\lambda\) ซึ่งทำให้สองค่าเท่ากัน: \(0.85 + 0.02\lambda = 0.80 + 0.20\lambda \Rightarrow 0.05 = 0.18\lambda \Rightarrow \lambda \approx 0.28\). ต่ำกว่านี้เลือก A สูงกว่านี้เลือก B — ตรงกับที่สไลด์สรุปว่า larger \(\lambda\) favors uncertain regions (exploration) while smaller \(\lambda\) favors regions with high predicted values (exploitation).

  • สูตร UCB \(= \mu + \lambda\sigma\): \(\lambda\) ใหญ่ = explore (เอื้อย่านที่ไม่แน่ใจ), \(\lambda\) เล็ก = exploit (เอื้อย่านที่คาดว่าคะแนนสูง) — จำทิศให้ถูก เพราะเป็นกับดักคลาสสิก

10. ใช้ KerasTuner: สร้าง HyperModel → เลือก Tuner → ค้นหา → ดึงผล

ปัญหาก่อน: §9 อธิบายอัลกอริทึมไว้หมดแล้ว แต่ถ้าต้องเขียนเองทั้ง loop (สุ่มค่า → สร้างโมเดล → เทรน → จดคะแนน → เลือกชุดถัดไป → ทำซ้ำ) ก็คงไม่ไหว. KerasTuner คือไลบรารีที่ทำ loop นั้นให้ เหลือหน้าที่ของเราแค่สองอย่าง: บอกว่า "โมเดลหน้าตาอย่างไรและปุ่มไหนให้ปรับได้บ้าง" กับ "ใช้อัลกอริทึมไหน".

สไลด์บอกว่า KerasTuner เป็น "general-purpose hyperparameter tuning library" และวิธีใช้เริ่มจากการเขียนฟังก์ชันที่คืนโมเดล Keras ที่ compile แล้ว (aka HyperModel) โดยฟังก์ชันนั้นรับอาร์กิวเมนต์ชื่อ hp สำหรับนิยาม hyperparameter ระหว่างสร้างโมเดล. สไลด์มีหมายเลขกำกับสองจุดในรูป: ❶ ชี้ที่ hp พร้อมคำอธิบายว่า "hp : HyperParameter object to be config to tune" และ ❷ ชี้ที่ return model พร้อมคำว่า "Compiled model with hyperparameters to tune". และย้ำว่ามี hyperparameter หลายชนิดให้ใช้: Int, Float, Choice, Boolean.

แนวคิดที่ต้องเปลี่ยนในหัว: แทนที่จะเขียน Dense(32, ...) ด้วยตัวเลขตายตัว เราเขียน Dense(hp.Int("units", 10, 50)) ซึ่งแปลว่า "ตรงนี้เป็นช่องว่าง ให้ tuner มาเติมเลขระหว่าง 10 ถึง 50 เอง". ฟังก์ชันนี้จะถูกเรียกใหม่ทุก trial และแต่ละครั้ง hp จะแจกค่าคนละชุด.

def build_model(hp):
    # build the model
    model = models.Sequential()
    Flatten(input_shape=(X.shape[1:],))
    for i in range(hp.Int("num_layers", min_value=1, max_value=2)):
        model.add(Dense(units=hp.Int("units_" + str(i), min_value=10, max_value=50, step=1),
                        activation=hp.Choice("activation", values=['relu', 'elu', 'selu'])))
        model.add(Dropout(hp.Float("dropout_" + str(i), 0, 0.5, step=0.1)))
    model.add(Dense(1, activation='sigmoid'))

    # compile the model
    model.compile(optimizer=keras.optimizers.Adam(learning_rate=hp.Float("lr", 1e-4, 1e-2, sampling='log')),
                  loss='binary_crossentropy',
                  metrics=['accuracy'])
    return model

ให้ ช่วงค้นหา 0.0001 ถึง 0.01 ซึ่งกว้าง 2 "ระดับ" (จาก \(10^{-4}\) ไป \(10^{-3}\) และจาก \(10^{-3}\) ไป \(10^{-2}\)) — ถามว่าสุ่มแล้วได้ค่าต่ำกว่า 0.001 กี่เปอร์เซ็นต์
  1. ขั้นที่ 1 — ถ้าสุ่มแบบเส้นตรง (uniform ธรรมดา)
    $$P(\text{lr} < 0.001) = \frac{0.001 - 0.0001}{0.01 - 0.0001} = \frac{0.0009}{0.0099} \approx 9.1\%$$

    แปลว่า 91% ของ trial จะไปกองอยู่ในช่วง 0.001–0.01 ทั้งที่ช่วง 0.0001–0.001 ก็สำคัญไม่แพ้กัน

  2. ขั้นที่ 2 — ถ้าสุ่มแบบ log (uniform บนสเกล \(\log_{10}\))
    $$P(\text{lr} < 0.001) = \frac{\log_{10}0.001 - \log_{10}0.0001}{\log_{10}0.01 - \log_{10}0.0001} = \frac{-3-(-4)}{-2-(-4)} = \frac{1}{2} = 50\%$$

แบบ log ให้โอกาสเท่ากันทุก "ระดับ" (\(10^{-4}\!\sim\!10^{-3}\) เท่ากับ \(10^{-3}\!\sim\!10^{-2}\)) ซึ่งเหมาะกับ learning rate เพราะสิ่งที่สำคัญคือขนาดหลัก (เลขชี้กำลัง) ไม่ใช่ผลต่างเชิงเส้น — การเปลี่ยนจาก 0.0001 เป็น 0.0002 (เท่าตัว!) สำคัญกว่าการเปลี่ยนจาก 0.0090 เป็น 0.0091 มาก ทั้งที่ระยะห่างเชิงเส้นพอๆ กัน. กฎง่ายๆ: hyperparameter ที่เราคิดเป็น "กี่ยกกำลัง" (learning rate, \(\lambda\) ของ L2, weight decay) ให้ใช้ sampling='log'; ที่คิดเป็น "กี่หน่วย" (จำนวน unit, dropout rate) ใช้แบบเส้นตรง.

validation 0.8936 สูงกว่า test 0.8845 อยู่เล็กน้อย (ต่างกัน 0.0091) ซึ่งสมเหตุสมผลและคาดหมายได้: เราคัดโมเดลที่ดีที่สุดจาก 211 ตัวโดยใช้ validation เป็นเกณฑ์ ตัวที่ชนะจึงมี "ความโชคดีกับ validation ชุดนั้น" ปนอยู่ด้วย. ตัวเลขที่ซื่อสัตย์คือ test set ที่ไม่เคยถูกใช้ตัดสินใจ และต้องใช้ครั้งเดียวตอนท้ายสุด — ถ้าเอา test มาวนเลือกโมเดลด้วย มันก็จะกลายเป็น validation อีกชุดหนึ่งทันที (data leakage).

11. ข้อควรระวังและแนวทางปฏิบัติ

สไลด์ปิดท้ายด้วยสามข้อที่ผูกกับทุกอย่างที่คำนวณมาแล้วในบทนี้:

  1. ไม่มีตัวเลขวิเศษ — สไลด์ขีดเส้นใต้ว่า no magic numbers that work for every problem ค่าที่ดีขึ้นกับ dataset และ task ที่ทำอยู่. นี่คือเหตุผลที่ตารางหน้า 22 ให้ "จุดเริ่มต้น" (32–256, 0.9/0.99/0.999) ไม่ใช่ "คำตอบ"
  2. ต้องเข้าใจว่าแต่ละปุ่มทำอะไร — การเลือกและจูนต้องอาศัยความเข้าใจ และสไลด์ทำตัวหนาขีดเส้นใต้ว่า Some degree of manual intervention and domain knowledge remain valuable in configuring the search and interpreting results. แปลว่าการจูนอัตโนมัติไม่ได้แทนที่คน — คนยังต้องเป็นคนตั้งขอบเขตการค้นหาและตีความผล
  3. Tuning Guidelines สองข้อ: (ก) Don't try to check all parameters manually เพราะ time consuming และไม่ได้ผล — ให้ใช้ global config กับ hyperparameter หลายตัว (คือล็อกค่าที่มีกฎชัดเจนไว้ทีเดียว ตามตารางหน้า 22); (ข) If the tuning is very slow, you might perform coarse to fine grained approach คือค้นแบบหยาบก่อน ดูผลว่าควรไปทางไหนต่อ แล้วค่อยรันใหม่ให้ละเอียดในย่านนั้น
คำนวณ: coarse-to-fine ช่วยย่นพื้นที่ค้นหาได้เท่าไร
ให้ รอบหยาบค้น learning rate ในช่วง \([10^{-4},\,10^{-2}]\) แบบ log (ตามโค้ดหน้า 29) แล้วพบว่าค่าที่ดีที่สุดอยู่แถว \(6.2\times10^{-4}\)
  1. ขั้นที่ 1 — วัดความกว้างของช่วงเดิมบนสเกล log
    $$\log_{10}\!\left(\frac{10^{-2}}{10^{-4}}\right) = \log_{10}(100) = 2 \text{ ระดับ}$$
  2. ขั้นที่ 2 — ตีกรอบใหม่ให้แคบลงรอบผู้ชนะ เช่น \([2\times10^{-4},\,10^{-3}]\)
    $$\log_{10}\!\left(\frac{10^{-3}}{2\times10^{-4}}\right) = \log_{10}(5) \approx 0.699 \text{ ระดับ}$$
  3. ขั้นที่ 3 — เทียบสองช่วง
    $$\frac{2}{0.699} \approx 2.9$$

พื้นที่ค้นหาเล็กลงราว 2.9 เท่า และที่สำคัญกว่าคือทุก trial ในรอบที่สองตกอยู่ในย่านที่รู้แล้วว่ามีแวว แทนที่จะเสียไปกับย่านที่พิสูจน์แล้วว่าแย่. ในสคริปต์ IMDB ที่อาจารย์รัน ผู้สอนทำแบบนี้จริง: รอบแรกค้นทุกอย่างพร้อมกันด้วย BayesianOptimization ได้ผู้ชนะเป็น 1 layer / 64 unit / dropout 0.4 / AdamW / lr ≈ 0.000423 (test accuracy 0.8845) จากนั้นรอบสองล็อกโครงสร้างไว้แล้วค้นเฉพาะ learning_rate ในช่วงแคบ \([2\times10^{-4},\,10^{-3}]\) คู่กับ weight_decay ∈ {1e-5, 1e-4, 1e-3} ⇒ search space เหลือแค่ 2 ตัวแปร และได้ผู้ชนะที่ lr = 0.000624, weight_decay = 1e-5 ซึ่งดันคะแนน test accuracy ขึ้นเป็น 0.8872 — ดีขึ้นอีก 0.0027 จากการค้นที่ถูกที่.

คำถาม 15Tuning guidelines
ตามสไลด์หน้า 32 ข้อใดสรุปคำแนะนำเรื่อง "coarse to fine grained approach" ได้ถูกต้องที่สุด?
ออกสอบสูง — ข้อความที่อาจารย์ทำสี
  • หน้า 32 ไม่มีข้อความทำสี แต่มีสองวลีที่อาจารย์ทำตัวหนาและขีดเส้นใต้ ซึ่งมีน้ำหนักเท่ากัน: no magic numbers that work for every problem และ Some degree of manual intervention and domain knowledge remain valuable in configuring the search and interpreting results. กับดักของข้อสอง: ตัวเลือกที่บอกว่า "การจูนอัตโนมัติทำให้ไม่ต้องใช้ความรู้เฉพาะด้านอีกต่อไป"
  • Tuning Guidelines สองข้อที่ขีดเส้นใต้ไว้: (1) Don't try to check all parameters manually — เปลืองเวลาและไม่ได้ผล ให้ใช้ global config; (2) If the tuning is very slow, you might perform coarse to fine grained approach — หยาบก่อน ดูทิศทาง แล้วค่อยละเอียด
  • คำถามเชิงสังเคราะห์ที่ออกได้: "ถ้า tuning ช้ามากควรทำอย่างไร" (ตอบ coarse-to-fine ไม่ใช่เพิ่มจำนวน trial), "ทำไมจึงยังต้องใช้คนทั้งที่จูนอัตโนมัติได้" (ตอบ ตั้งขอบเขตการค้นหาและตีความผล)

ชัยชนะของบทเรียนนี้
คุณควร (1) ไล่ตารางของ EarlyStopping ได้ทีละ epoch พร้อมบอกว่า patience/min_delta ทำอะไรและ weight ของ epoch ไหนถูกคืนมา; (2) คำนวณว่า ModelCheckpoint(save_freq=6) เซฟไฟล์ชื่ออะไรบ้าง และอธิบายความต่างของ save/save_weights/save_best_only/BackupAndRestore; (3) คำนวณ learning rate ของ LearningRateScheduler (รวมกับดักการคูณซ้อน 0.03 → 0.027 → 0.0243 → 0.019683) และของ ReduceLROnPlateau (0.03 → 0.003 → 0.001); (4) เขียนอาร์กิวเมนต์ของ TensorBoard callback ได้ครบและบอกว่าแต่ละตัวคุมแท็บไหน; (5) อธิบายด้วยตัวเลขว่าทำไม RandomUniform(0,1) + tanh ทำให้ gradient หาย และ Batch Norm แก้ได้อย่างไร; (6) เปรียบเทียบ Grid/Random/HyperBand/Bayesian ด้วยตัวเลขจริง (911,430 ชุด เทียบกับ 211 trial; งบ 405 เทียบกับ 6,561; UCB ที่ \(\lambda\) ต่างกัน) และเขียนโครง build_model(hp) ของ KerasTuner ได้เอง.
